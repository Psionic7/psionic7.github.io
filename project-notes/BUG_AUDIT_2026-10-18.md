## B01 — 잘못된 날짜가 전체 기간 조회로 바뀜

위치: [TransactionPage.jsx](../src/TransactionPage.jsx#L48), [data.js](../src/data.js#L23), [useDistrictDatasets.js](../src/weekly/useDistrictDatasets.js#L20).

**재현:** 동네 거래에서 풍덕천동, 직접 기간 2026-09-01~2026-09-30을 선택한 뒤 시작일을 비운다.

**관찰:** ‘올바른 조회 날짜를 선택해 주세요.’가 표시되는데도 2005-12, 2006-01~05의 월별 자료 요청 6개가 발생했다. 첫 묶음은 요청을 차단해 전체 과거 자료가 실제로 내려받아지는 것을 막았다.

**원인:** `periodBounds`가 null을 반환해도 자료 로더는 호출된다. 시작·종료 조건이 빠진 요청을 `loadDistrict`가 전체 기간 조회로 처리한다. 성공 응답을 허용하면 다음 묶음도 순차적으로 요청하는 구조다. 화면은 결과를 숨기지만 요청은 이미 시작된다. UI에서 기간을 바꿔도 이미 시작한 로더를 중단하는 경로가 없다.

**영향:** 날짜를 수정하는 일상적인 조작으로 불필요한 네트워크 사용과 메모리 소비가 발생한다. 동네·단지 거래가 공유하는 조회 경로에 영향을 준다.

**수정 방향:** 날짜 유효성 검증을 자료 요청 전에 적용한다. 선택 목록에 필요한 카탈로그 조회와 거래 조회를 분리하고, 잘못된 범위를 ‘전체 기간’으로 해석하지 않게 한다.

## B02 — 여러 탭에서 즐겨찾기 유실

위치: [preferences.js](../src/preferences.js#L104), 같은 파일의 저장 효과 109~111행.

**재현:** 즐겨찾기가 없는 격리 저장소에서 두 탭을 먼저 연다. A 탭에서 단지 A를 저장한 뒤 B 탭에서 단지 B를 저장한다.

**관찰:** 저장된 단지 ID 배열이 `[A]`에서 `[B]`로 바뀌었다. A 탭은 계속 즐겨찾기 상태로 표시하지만, 새로고침하면 A가 사라진다.

**원인:** 훅이 처음 읽은 배열을 각 탭의 상태로 유지하며 다른 탭의 `storage` 변경을 구독하지 않는다. 저장 시 최신 문서의 다른 필드는 읽지만, 해당 즐겨찾기 배열은 탭의 오래된 배열로 통째로 덮어쓴다. 동 즐겨찾기도 같은 저장 방식이다.

**영향:** 여러 탭을 사용하는 정상 흐름에서 사용자가 추가한 즐겨찾기가 유실될 수 있다.

**수정 방향:** 탭 사이 변경을 동기화하고 추가·삭제 작업을 최신 저장 상태에 적용한다. 단순 배열 합치기는 삭제한 항목을 되살릴 수 있으므로 추가와 삭제 의미를 모두 검증해야 한다. 거의 동시에 쓰는 경우의 충돌 정책도 필요하다.

## B03 — 화면 스크립트 실패 후 전체 빈 화면

위치: [App.jsx](../src/App.jsx#L18), 같은 파일의 `Suspense` 156~163행.

**재현:** 첫 화면을 정상 로드하고 아파트 지도용 JS 청크 요청을 실패시키며 지도로 이동한다.

**관찰:** `Failed to fetch dynamically imported module` 오류 이후 `.public-shell` 개수가 0이 되고 본문 텍스트도 빈 문자열이 됐다. 재시도 버튼도 없었다. 처음에는 로딩 문구가 보이므로 비동기 실패가 완료될 때까지 기다려 재확인했다.

**원인:** `Suspense`는 로딩 중 표시만 담당한다. 지연 로딩 실패를 받는 Error Boundary나 Vite 청크 로드 오류 복구 처리가 없어 루트 화면이 제거된다.

**영향:** 불안정한 연결이나 배포 전 페이지가 참조하는 이전 해시의 청크가 사라진 경우, 탭 이동으로 사이트 전체를 사용할 수 없게 된다. 장애 주입으로 확인했으며 운영 중 실제 발생 여부는 확인하지 않았다.

**수정 방향:** 화면 경계에서 오류를 잡고 메뉴와 복구 안내를 유지한다. 새로고침·재시도 동작을 제공하되 무한 새로고침은 피한다. 이미 실패한 `React.lazy`의 캐시도 고려해야 한다.

## B04 — 자료 목록의 잘못된 구조가 렌더링 오류로 이어짐

위치: [App.jsx](../src/App.jsx#L51), [domain.mjs](../src/domain.mjs#L131).

**재현:** `/data/manifest.json`에 HTTP 200, JSON `{}`를 반환한다.

**관찰:** `Cannot read properties of undefined (reading 'forEach')` 오류 후 전체 화면이 비고 재시도 안내가 없어졌다.

**원인:** 요청 성공과 JSON 파싱 성공만 확인하고 상태에 넣는다. 필수 `regions`, `districts`, `months` 등의 구조를 확인하지 않아 이후 렌더링에서 예외가 난다.

**영향:** JSON 형식은 맞지만 필수 구조가 없는 응답에 대한 복구가 불가능하다. 정상 게시 경로의 검사가 있어 B03보다 발생 조건이 제한적이며, 현재 정상 공개 파일이 깨졌다는 발견은 아니다.

**수정 방향:** 루트 자료를 사용하기 전에 스키마를 검증하고, 검증 실패를 기존 자료 로드 실패 UI로 연결한다. B03의 오류 경계는 최후 복구 수단으로 함께 적용한다.

## B05 — 대시보드의 동별 자료 제공 여부 판정 불일치

위치: [dashboard/model.mjs](../src/dashboard/model.mjs#L25), [coverage.js](../src/coverage.js#L1).

**재현:** 공개 자료의 고기동(`dong_41465104`)을 즐겨찾기하고 관심 목록 대시보드를 연다.

**관찰:** 공통 `hasTradeCoverage` 결과는 false지만 대시보드는 `ready`, 거래 0건, 미수집 0곳으로 판정한다. 실제 카드도 ‘이전 기간과 동일 / 0건’으로 표시했다.

**원인:** 대시보드는 시군구 자료 존재만 확인한다. 다른 조회·지도 화면은 시군구 자료에 해당 동이 포함되는지도 확인한다.

**영향:** 앱 자체에서 자료 제공을 확인하지 못하는 상태와 실제 거래 0건을 화면마다 다르게 설명한다. 이것만으로 고기동의 원천 거래가 누락되었다고 단정할 수는 없다. 현 메타데이터의 동 목록이 거래 행에서 만들어지므로, 정상적으로 수집했지만 과거 거래가 없는 경우도 구분할 필요가 있다.

**수정 방향:** 화면들의 수집 범위 판정을 통일한다. 장기적으로는 ‘거래가 존재하는 동’과 ‘수집 완료한 동·월’을 별도 메타데이터로 관리해 정상 0건과 미확인을 구분한다.

## B06 — 저장 실패 시 조회 화면과 공유 주소가 달라짐

위치: [query-state.js](../src/query-state.js#L15), [App.jsx](../src/App.jsx#L125).

**재현:** 브라우저 저장 쓰기를 실패시키고 동네 거래 최소 전용면적을 80㎡로 입력한다.

**관찰:** 화면의 입력값은 80인데 URL의 `min`은 빈 문자열이었다. 저장 실패 안내는 표시됐지만 공유 주소는 현재 조건을 반영하지 못했다.

**원인:** 실제 필터는 React 상태에 있지만 URL은 `readPreferences`로 저장소를 다시 읽어 구성한다. 저장 실패 또는 오래된 저장 상태와 화면 상태가 분리된다.

**영향:** 공유 주소를 받은 사용자가 보내는 사람과 다른 조건의 결과를 보게 된다. 저장이 차단되거나 용량이 부족한 경우에 재현된다.

**수정 방향:** 공유 주소는 현재 화면의 필터 상태로 만든다. 저장 성공 여부와 주소 생성의 정확성을 분리한다.

## B07 — 큰 기존 설정의 조회 초기화가 즐겨찾기도 삭제

위치: [preferences.js](../src/preferences.js#L14), 같은 파일의 `resetQueries` 52행.

**재현:** 격리 저장소에 version 1 구조이며 2,097,249자인 설정 문서와 viewer 즐겨찾기 필드를 넣는다. 일반 저장을 시도한 뒤 조회 조건 초기화를 실행한다.

**관찰:** 일반 저장은 false를 반환하고 기존 문서를 보존했다. 반면 조회 초기화 후 문서는 `{"version":1,"scopes":{"viewer":{}}}`로 바뀌었다.

**원인:** 일반 저장은 엄격한 읽기로 크기 초과 시 멈추지만, 초기화는 읽기 실패를 빈 문서로 바꾸는 기본 모드를 쓴다. 읽지 못한 즐겨찾기까지 없는 것으로 취급해 덮어쓴다. 초기화 전 스냅샷도 같은 기본 읽기를 사용하므로 되돌리기로 원본을 복원할 수 없다.

**영향:** 이전 버전·수동 저장 등으로 이미 크기 제한을 넘긴 설정이 있는 드문 경우에 ‘조회 조건만 초기화’의 보존 약속이 깨진다. 현재 정상 저장 함수가 이런 큰 문서를 새로 만든다는 뜻은 아니다.

**수정 방향:** 원본을 읽지 못하면 초기화·스냅샷 동작도 안전하게 중단하고 실패를 알린다. 필요하면 원본 백업 후 검증된 viewer만 복구하는 절차를 제공한다.

## B08 — 관리자 설정 확인 버튼의 API 없음

위치: [ApartmentMasterPanel.jsx](../admin/ApartmentMasterPanel.jsx#L10), [Admin.jsx](../admin/Admin.jsx#L10), [server/index.mjs](../server/index.mjs#L158).

**재현:** ‘아파트 수집 설정 확인’ 버튼이 보내는 것과 같은 `POST /api/reload`를 임시 관리자 서버에 올바른 CSRF 헤더로 보낸다.

**관찰:** HTTP 404, `존재하지 않는 관리자 API` 응답을 받았다.

**원인:** 화면은 `action('reload', {}, ...)`를 호출하지만 서버에 해당 API가 없다. 현재 상태를 읽는 기존 경로는 `GET /api/state`다.

**수정 방향:** 실제로 필요한 상태 갱신 동작과 연결한다. 다른 패널의 기존 상태 재조회와 동일한 API 호출을 사용할 수 있다.

## B09 — 로컬 관리자 빌드가 필수 준비 단계 생략

위치: [server/index.mjs](../server/index.mjs#L147), [package.json](../package.json#L8), [prepare-browser-data.mjs](../scripts/prepare-browser-data.mjs#L21), [check-public.mjs](../scripts/check-public.mjs#L63), [apartment-map-data.js](../src/apartment-map-data.js#L26).

**확인:** 정상 `pnpm build`는 브라우저 자료 준비 → Vite 빌드 → 마무리를 실행한다. 관리자 `/api/build`는 Vite만 직접 실행하고 `.nojekyll` 및 공개 파일 검사를 따로 처리한다. Vite 설정은 준비된 파일을 읽을 뿐 생성하지 않는다.

**원인과 영향:** 지도 경계 조각과 통합 검색 인덱스를 만드는 준비 스크립트가 생략된다. 새 체크아웃처럼 무시된 `/public/map-data/`가 없거나 지도 자료가 갱신된 상태에서는 지도 경계 파일이 없거나 버전이 맞지 않을 수 있다. `/query-data/`는 내보내기 경로에서도 일부 생성되지만, 새 통합 검색 인덱스는 해당 준비 단계에서 만든다. 검색이 카탈로그 대체 경로로 동작하더라도 마스터 이름·별칭 통합 결과는 달라질 수 있다.

공개 검사도 지도 조각 폴더가 **있을 때만** 검사하므로 폴더 자체가 없는 경우를 잡지 못한다. 정상 GitHub Actions의 `pnpm build` 경로와 구분되는 **로컬 관리자 빌드의 문제**다. 실제 수집 DB·빌드 산출물을 바꾸지 않기 위해 이 버튼의 전체 실행은 하지 않았다.

**수정 방향:** 관리자와 CLI가 동일한 빌드 진입점을 사용하도록 통합한다. 최종 산출물에서 지도·검색 인덱스의 존재와 원본 버전 일치까지 확인한다.

## B10 — 건축물대장 재시도가 예외 없이 종료될 수 있음

위치: [building-registry.mjs](../server/building-registry.mjs#L22), 같은 파일의 응답 읽기 예외 처리 27행.

**재현:** 첫 6회는 네트워크 실패, 마지막 2회는 HTTP 성공 후 본문 읽기 실패를 반환하는 가짜 fetcher를 주입한다. 지연은 0으로 설정한다.

**관찰:** 총 8회 시도 후 함수가 예외 없이 undefined를 반환했다.

**원인:** 반복은 attempt 0~7인데 본문 읽기 실패의 마지막 시도 판정은 `attempt===5`다. 6~7번째 인덱스에서 실패하면 `continue` 후 반복이 끝나 반환값이 없어진다. 호출자는 `{total, items}`를 가정하므로 원인을 알기 어려운 후속 TypeError로 수집이 중단될 수 있다.

**수정 방향:** 마지막 시도 기준을 통일하고 재시도 소진 후 반드시 명확한 오류를 던진다. 네트워크 실패와 응답 읽기 실패가 섞이는 테스트를 추가한다.

## 결과물과 남은 범위

위 10건의 재현 조건과 우선순위를 기록했다. 감사 과정에서 추측만 생겼거나 실제 자료에서 확인되지 않은 문제는 확정 목록에 넣지 않았다. 동일 실거래 행을 무조건 중복 제거하는 변경처럼 기존 테스트가 의도한 동작을 오류로 분류하지 않았다.

실제 외부 API의 순간 장애·호출 한도, 운영 환경의 인증·권한 변경, 장시간 동시 수집, 모든 기종의 터치 동작은 이번 점검으로 검증하지 않았다. 기존 테스트 통과를 이 범위의 정상 보장으로 해석하지 않아야 한다.
