# 아파트 식별 정보 통합

## 문제와 구현 계획

삼성1차가 건축물대장에는 `삼성아파트`, 실거래에는 `삼성1`, 주소 API에는 `삼성래미안1차아파트`, 네이버에는 `삼성1차`로 기록되어 매물 검색에서 누락됐다. 기존 건축물대장 ID를 공통 키로 유지한다.

- [x] `apartment_identity`에 대표 이름, 행정구역, 지번, 도로명주소, 우편번호와 출처를 저장한다.
- [x] 기존 `apartment_aliases`를 검증된 이름 사전으로 사용하고, `apartment_identity_addresses`에 주소 API의 여러 도로명주소와 건물관리번호를 저장한다.
- [x] 건축물대장, 주소 API의 기존 응답, 주소가 검증된 실거래·네이버 매물에서 정보를 이관한다. 알 수 없는 우편번호는 NULL로 둔다.
- [x] 매물 수집, 거래 연결, 검색·지도 데이터 생성에서 공통 아파트 정보 모듈을 사용한다. 별칭·주소·우편번호로 후보를 조회하고 모호한 연결은 거부한다.
- [x] 동명이인 단지, 같은 우편번호, 서로 다른 지번, 재실행, 삼성1차 회귀 테스트와 실제 DB 검증을 수행한다.
- [x] AGENTS.md에 공통 정보 조회와 검증된 별칭 등록 지침을 추가한다.

## 데이터 소유권과 연결 규칙

`server/apartment-identity.mjs`가 통합 테이블의 생성·갱신·조회·연결을 담당한다. 기존 `apartment_complexes.apartment_id`가 기본키다. 기존 거래 원문과 건축물대장 원문은 변경하지 않는다.

검색은 후보 목록을 반환한다. 데이터 연결은 검증된 ID 또는 행정구역·법정동·지번과 이름 사전의 교집합이 한 단지일 때만 허용한다. 도로명주소는 검증된 주소 사전을 사용한다. 우편번호 단독, 이름 단독, 임의 부분 일치로 자동 연결하지 않는다.

주소 API에 같은 지번의 여러 건물 주소가 있으면 모두 저장한다. 대표 도로명주소와 일치하는 건물의 우편번호를 우선 사용하고, 대표 건물을 고를 수 없으면 후보 우편번호가 모두 같을 때만 단지 우편번호를 확정한다.

네이버 이름과 단지 번호는 실제 주소 검증을 통과한 관찰에서만 등록한다. 수집·조회에 실패한 결과를 별칭이나 연결 근거로 사용하지 않는다. 사용자가 확인한 별칭은 주소와 함께 검토 가능한 데이터 파일에 기록한다.

## 테이블과 조회

실제 SQL 테이블은 작업 DB `local/my_real_estate.sqlite3`에 있다. 정적 웹 화면은 비밀 값 검사를 통과한 `public/apartment-identity/catalog.json`을 참조한다. 원본 주소 API 응답과 작업 DB 전체는 공개하지 않는다.

| 테이블·뷰 | 내용 |
| --- | --- |
| `apartment_identity` | 단지 ID, 대표 이름, 행정구역·법정동, 대표 지번·도로명주소, 확인한 우편번호와 출처, 검증된 네이버 번호·이름, 활성 상태·갱신 시각 |
| `apartment_aliases` | 단지 ID에 연결한 여러 이름과 검증 출처. 기존 테이블을 공유한다. |
| `apartment_identity_addresses` | 같은 단지의 여러 실제 주소, 건물관리번호·도로명코드, 우편번호, 출처·관찰 시각 |
| `apartment_information` | 대표 정보와 이름 사전을 함께 읽는 SQL 뷰 |

```sql
SELECT apartment_id, canonical_name, name_aliases_json,
       road_address, postal_code, naver_complex_no
FROM apartment_information
WHERE apartment_id = 'hub:11161181462';
```

이름·주소·우편번호로 후보를 확인한다.

```powershell
pnpm data:identities --query "수지삼성래미안1차"
```

검토한 별칭을 추가할 때는 `automation/apartment-aliases.json`에 기존 ID와 검증한 주소를 기록한다. 주소가 대장과 다르면 갱신 전체가 롤백된다. 이후 `pnpm data:identities`, `pnpm data:export`, `pnpm data:verify`, `pnpm build`, `pnpm check:publish`를 실행한다.

## 실행 결과와 재발 방지

- 기존 ID를 유지한 467개 아파트를 이관했다. 공식 주소 응답으로 385개의 우편번호를 확인했으며 나머지 82개는 NULL이다. 작업 DB는 이관 전에 `local/apartment-identity-before.sqlite3`로 백업했다.
- 삼성1차의 7개 표기를 같은 ID에 연결했다. 수풍로 9·13, 우편번호 16818, 네이버 단지 2219를 보존했다.
- 일일 수집은 통합 테이블의 별칭·검증된 네이버 번호를 사용하고, 새로운 관찰에 성공하면 같은 테이블을 갱신한다. 저장 번호를 사용해도 주소 검증은 다시 수행한다.
- 실거래 연결은 기존 지번·준공연도 검증을 유지하고 통합 정보와 모순되는 단일 연결은 재검토한다. 같은 단지의 여러 건축물대장 ID를 임의로 합치지 않는다.
- 검색·지도·단지 선택은 공통 별칭과 우편번호를 사용한다. 검색 목록에서 통합 테이블의 대표 이름·별칭·우편번호가 빠지면 빌드와 게시 검증이 실패한다.
- 아파트 대장이 없는 이전 클라우드 DB로 실거래를 내보내도 기존 식별 정보를 빈 목록으로 덮어쓰지 않는다.
- 회귀 테스트는 `tests/apartment-identity.test.mjs`, `tests/data-integrity.test.mjs`, `tests/explore-flow.test.jsx`에 있다. 실제 화면에서 별칭·우편번호·도로명주소 검색과 삼성1차 매물 39건 연결을 확인했다.
