# 상록우성 네이버 수집 실패 원인 분석

분석일: 2026-11-10. 대상은 사용자가 제공한 [상록우성 단지번호 2645](https://fin.land.naver.com/complexes/2645?articleTradeTypes=A1-B1&tab=transaction)다.

이 문서는 수정 전 분석 기록이다. 후속 구현에서 일반 Chrome으로 실제 매매 광고 255건·제공자 묶음 31개·2페이지를 수집했다. 현재 결과와 변경 내용은 [구현·실제 수집 검증](naver-fin-collection-implementation-2026-11-10.md)에 있다.

현재 확인한 상록우성의 단지번호·주소는 로컬 확정 연결과 일치한다. 기존 수집기의 주소·화면·응답 규칙이 새 서비스와 맞지 않는 문제가 확인됐다. 새 서비스의 브라우저 후속 요청에서는 HTTP 429도 관측해 중단했다. 매매 매물 전체 수집 성공이나 매물 0건을 확인한 결과는 아니다.

## 1. 단지번호와 로컬 연결은 일치한다

insane-search로 새 서비스의 공개 응답을 읽었다. 서버에서 내려온 화면 데이터의 `GET /complex` 조회 키에는 `complexNumber: 2645`가 있고 상태는 `success`였다.

| 항목 | 실제 공급자 응답 | 기존 로컬 확정 정보 |
| --- | --- | --- |
| 네이버 단지번호 | `2645` | `2645` |
| 이름 | 상록우성 | 상록마을, 우성 원천 연결 |
| 법정동 | 정자동 | 정자동 |
| 지번 | 121 | 121 |
| 도로명 | 내정로 55 | 경기도 성남시 분당구 내정로 55 (정자동) |
| 로컬 root | 공급자 응답의 ID와 구분 | `hub:10891118021` |

실제 관측 좌표는 경도 `127.112097`, 위도 `37.364204`다. 이 분석으로 새 연결을 승인하거나 로컬 값을 덮어쓰지 않았다. 기존 연결과 이번 관측의 일치만 확인했다. 다른 상록마을 단지로 결과를 확대하지 않는다.

## 2. 기존 주소의 실제 브라우저 이동은 실패한다

기존 수집기와 같은 주소를 요청했다.

`https://new.land.naver.com/complexes/2645?a=APT&b=A1&e=RETAIL`

insane-search의 HTTP 단계에서는 200과 초기 HTML이 반환됐다. 그러나 초기 단지 상태는 `complex: null`이었다. 단지명·주소가 없으므로 이것만으로 페이지 오류를 확정하지 않았다.

이후 nodriver와 시스템 Chrome으로 같은 주소를 열었다. 최종 주소가 `https://new.land.naver.com/404`로 바뀌었고, 화면에 주소가 변경되거나 삭제되어 요청한 페이지를 찾을 수 없다는 안내가 표시됐다. 이 오류 화면의 HTTP 응답도 200이었다.

따라서 이번 실행에서는 기존 주소의 실제 실패를 확인했다. HTTP 200을 페이지 정상이나 매물 수집 성공으로 처리하면 안 된다. 앞선 로컬 테스트에서 확인한 페이지 이동 판정 버그만으로 이번 실패를 설명할 수 없다.

## 3. 새 주소는 현재 수집기에 그대로 넣을 수 없다

새 주소의 HTTP 응답에서는 단지정보를 읽을 수 있었다. 최종 주소는 단지 선택 정보를 담은 `/map?layer=...`였다. 기존 수집기는 상세 화면이 계속 `/complexes/<번호>`에 있다고 가정한다.

| 구분 | 기존 수집기 가정 | 이번 관측 |
| --- | --- | --- |
| 허용 도메인 | `new.land.naver.com` | 사용자가 제공한 `fin.land.naver.com` |
| 상세 화면 경로 | `/complexes/<번호>` | 새 서비스에서 `/map?layer=...`로 이동 |
| 상세 요소 | `#complexTitle` | 새 초기 HTML에 해당 요소 없음 |
| 목록 요소 | `#articleListArea`, `#address_group2` | 새 초기 HTML에 해당 요소 없음 |
| 데이터 경로 | `/api/complexes/<번호>`, `/api/articles/complex/<번호>` | 브라우저에서 `/front-api/v1/complex` 요청 관측 |
| 단지 데이터 형식 | `complexNo`, `complexDetail`, `realEstateTypeCode` | 조회 매개변수 `complexNumber`, 응답 `result`, `type`, 중첩 `address`와 `coordinates` |

`createSystemChromeListingSource`에 새 도메인을 넘기는 로컬 검사를 실행했다. Python이나 브라우저를 실행하기 전에 `매물 브라우저 주소를 확인하세요.` 오류로 거부됐다. 주소 문자열 하나를 바꾸는 수정만으로 전환이 끝나지 않는다.

기존 연결 URL 검증과 일부 응답 정규화도 옛 도메인·형식에 묶여 있다. 실제 새 응답을 현재 내부 매물 형식으로 바꾸는 수집기와 검증기 수정이 필요하다.

관련 코드:

- `server/naver-system-chrome.mjs`: 도메인 허용 검사와 Python 응답 정규화.
- `scripts/naver-system-chrome.py`: API 경로 필터, 상세·목록 요소, 현재 URL 판정.
- `server/naver-browser-collector.mjs`: 기존 API와 상세 화면 요소 가정.
- `src/naver-listings.mjs`: 저장 단지 링크 검증.

## 4. 새 서비스의 후속 요청에서는 429가 발생했다

새 매매 화면을 nodriver와 시스템 Chrome으로 열었다. HTML 문서는 HTTP 200이었지만 다음 공개 데이터 요청들이 HTTP 429를 반환했다.

- `/front-api/v1/complex`
- `/front-api/v1/legalDivision/searchByCoordinate`
- 같은 화면에서 발생한 다른 사용자 상태·배너 관련 요청.

최종 화면은 `financial.pstatic.net/404.html` 오류 안내였다. 제한 응답을 관측한 뒤 브라우저 실행을 종료했다. 제한을 우회하거나 다른 세션으로 반복 수집하지 않았다.

이 실행에서는 화면의 오류 주소보다 앞선 429를 원인으로 보존해야 한다. 단지 ID 오류나 실제 매물 0건으로 바꾸면 안 된다. 모든 사용자나 모든 환경에서 같은 제한이 발생한다는 뜻은 아니다. 제한의 구체적인 적용 범위·지속 시간도 현재 증거로 확정할 수 없다.

기존 Python 수집기의 오류 검사는 옛 `/api/...` 경로로 한정돼 있다. 따라서 새 서비스의 `/front-api/v1/...` 제한 응답을 그대로는 포착하지 못한다. 새 도메인 지원 시 오류 감지도 같이 바꿔야 한다.

## 5. 페이지 이동 판정 버그도 별도로 존재한다

`Collector.collect`는 이동 요청 직후 이전 화면의 주소를 읽을 수 있다. 로컬 모의 탭으로 실제 함수를 실행했다.

| 이동 중 남은 이전 화면 | 반환값 | 다음에 읽으면 보일 화면 |
| --- | --- | --- |
| `/404` | `site_unavailable` | 요청한 `2645` |
| 다른 단지 `2623` | `address_mismatch` | 요청한 `2645` |
| 요청한 단지 `2645` | 성공 | 요청한 `2645` |

상세 정보 확인 함수 `inspect`에는 새 문서의 로더를 확인하는 코드가 있지만 전체 매물 수집 함수 `collect`에는 같은 확인이 없다. 새 화면이 확인된 뒤에만 주소·단지·오류를 판정하도록 수정해야 한다.

이번 실제 브라우저 진단에서는 기존 도메인의 오류 화면 자체도 확인했다. 이 모의 테스트를 근거로 실제 사이트의 오류가 전부 이동 시점 때문이라고 결론 내리지 않는다.

## 이 문제의 해결 순서

1. 기존 로컬 아파트 ID와 네이버 단지번호 `2645`를 유지한다. 수집 경로 문제를 단지 매핑 변경으로 해결하지 않는다.
2. 네트워크 접근과 내용 검증을 분리한다. insane-search의 200·`weak_ok`는 접속 단계의 결과다. 단지번호·실제 주소·단지 데이터 확인과 매물 수집 완료 검증은 프로젝트 수집기가 수행한다.
3. 새 서비스용 수집 경로를 추가한다. 도메인, `/map` 이동, 새 데이터 경로·형식을 지원하고 실제 단지번호와 관측 주소를 검증한다. 아직 관측하지 못한 매물 API 경로나 페이지 형식을 임의로 가정하지 않는다.
4. 새 문서로 이동했는지 확인한 뒤 실패를 판정한다. 429·403·보안 확인을 오류 화면보다 우선 기록하고, 승인 연결과 이전 광고를 보존한다.
5. 접근 제한이 해소된 정상 실행에서 매매 전용 목록과 다음 페이지를 관측한다. 광고 ID·단지번호·가격·면적·동·층·관측 시각을 검증하고 마지막 페이지까지 확인한다. HTML의 초기 0이나 로딩 표시를 매물 0건으로 저장하지 않는다.
6. 상록우성 한 단지에서 정상 자료·전체 페이지 검증이 끝난 후 다른 로컬 확정 ID로 범위를 넓힌다.

현재는 분석과 진단 스크립트만 추가했다. 운영 수집기·원본 DB·공개 스냅샷은 수정하지 않았다. 커밋·푸시도 하지 않았다.

## 재확인 자료

원문과 요청 결과는 비공개 `local/naver-route-analysis/`에 있다.

- `old-result.json`, `old-raw.html`: 기존 주소의 HTTP 응답.
- `info-result.json`, `info-raw.html`, `articles-result.json`, `articles-raw.html`: 새 서비스의 HTTP 응답.
- `server-query-summary.json`: 공개 서버 렌더링 데이터에서 읽은 단지번호·주소와 조회 상태.
- `browser-results.json`, `browser-old-state.json`, `browser-new-state.json`: 실제 브라우저 최종 주소·화면·네트워크 상태.

진단 스크립트는 `local/analyze-naver-routes.py`, `local/diagnose-naver-browser.py`, `local/summarize-naver-routes.mjs`다. 페이지 이동 오판 재현은 `local/check-naver-navigation-race.py`다. 스크립트 종료코드 0은 진단이 끝났다는 뜻이며 매물 수집 성공을 뜻하지 않는다.
