# 상세 API 전환 후 단지별 거래 조회 누락

2026-11-13 배포 자료와 로컬 확정 기준본을 읽기 전용으로 비교한 당시 진단이다. 이후 사용자 승인으로 수행한 2026-11-14 로컬 연결 복구·재발 검사 결과는 [공식 단지 연결 복구 기록](molit-source-connection-repair-2026-11-14.md)을 참조한다. 아래의 미수정 상태 설명은 진단 시점의 기록이다.

## 확인된 원인

상세 API 전환 후 공식 단지 ID `aptSeq`가 있는 거래가 늘었지만, 로컬 확정 기준본의 공급자 연결표는 일부만 이관된 상태다. 배포 데이터에는 거래가 남아 있으나 대장 단지별 조회에서 제외된다.

`server/apartment-baseline-runtime.mjs`의 `baselineTradeBinding`은 `aptSeq`가 있으면 `payload.providers.molit[aptSeq]`에 승인된 원천 단지만 사용한다. 번호가 없을 때는 기존 원천 단지를 사용한다. 따라서 같은 계약에 공식 번호가 보강돼도 그 번호가 연결표에 없으면 기존 배정 대신 `unresolved`를 반환한다.

`src/housing-identity.mjs`의 `identityTradeMatches`는 대장 단지·주소 구획 조회에서 `unresolved` 배정을 제외한다. 이 조건 자체는 미승인 단지의 자동 연결을 막는 운영 규칙과 일치한다. 문제는 공식 번호의 로컬 연결 이관을 완료하지 않은 상태로 상세 API 수집을 확대한 전환 절차다.

기준본 `2231257a459bd8c29b85b48f1faba05d0f4cf4fdbcd3989dac9e4ab49d511a2d`의 실거래 공급자 연결은 169개다. 앞서 로컬에서 상세 API를 받은 분당구 일부 월의 관측 범위였으며 영통구·수지구에는 승인된 공식 번호가 없다. 배포 수집기가 과거 월과 최근 월을 상세 API로 갱신하면서 연결 누락의 영향이 확대됐다.

## 배포 자료와 조회에서 재현한 영향

확인한 배포 자료는 총 344,779건이며 생성 시각은 2026-11-13 07:00 KST다. 비교 로컬 자료는 344,537건이다. 배포된 3개 구의 원천 JSON은 모두 manifest의 파일 해시와 건수에 일치했다.

거래 내부 ID는 로컬과 클라우드에서 다를 수 있으므로, ID를 단독으로 대조하지 않았다. 지역·계약월·계약일·단지명·법정동·지번·가격·면적·층·준공연도·해제 상태가 모두 같은 계약을 중복 개수까지 대응시켰다. 그중 기존 확정 배정이 `unresolved`로 바뀐 결과는 다음과 같다.

| 지역 | 같은 계약의 배정이 미확정으로 바뀐 행 | 영향을 받은 대장 단지 |
| --- | ---: | ---: |
| 수원시 영통구 | 3,648 | 49 |
| 성남시 분당구 | 381 | 21 |
| 용인시 수지구 | 11,868 | 179 |
| 합계 | 15,897 | 249 |

이 숫자는 전체 자료의 삭제 건수나 모든 미연결 거래의 합계가 아니다. 계약 내용이 같고 로컬에서는 확정 배정이 있던 거래 중 조회 배정이 미확정으로 내려간 행만 센 결과다. 배포 자료 중 승인되지 않은 공식 번호를 가진 행은 총 30,539건이며, 기존부터 미확정이었던 행과 신규 계약도 포함한다.

실제 배포 원천·배정 파일을 `housingBindingsMap`, `apartmentQueryRegion`, `weeklyResultRows`에 전달해 화면과 같은 날짜 제한 없는 최근 유효 거래 20건 조회를 실행했다.

| 단지 | 로컬 비교본의 최신 조회 거래 | 배포본의 최신 조회 거래 |
| --- | --- | --- |
| 성복역 롯데캐슬 골드타운 | 2026-10-26 | 2025-11-30 |
| 광교중흥에스클래스 | 2026-10-30 | 2025-11-26 |
| 샛별마을 대장 단지 | 2026-06-17 | 2025-11-26 |

최근 거래는 원천 파일에 존재한다. 상세 API로 갱신한 거래가 조회 조건에서 제외되면서 예전 기본 API 자료가 최근 20건을 채웠다. 이번 세션에는 연결 가능한 브라우저가 없어 화면의 시각적 재현은 수행하지 못했으며, 실제 배포 파일과 애플리케이션 조회 함수의 실행으로 재현했다.

## 기본·상세 API의 값은 조사 범위에서 일치

인증키는 Git 제외 비밀 파일만 참조했다. 응답 URL이나 키는 결과에 기록하지 않았다. 다음 지역·월을 실제 기본·상세 API로 각각 요청해 공통 정규화 필드와 중복 개수를 비교했다.

| 지역·계약월 | 기본 API | 상세 API | 공통 필드가 일치한 행 |
| --- | ---: | ---: | ---: |
| 영통구 2026-11 | 110 | 110 | 110 |
| 분당구 2026-11 | 37 | 37 | 37 |
| 수지구 2026-11 | 73 | 73 | 73 |
| 분당구 2026-05 | 530 | 530 | 530 |
| 수지구 2026-07 | 635 | 635 | 635 |
| 합계 | 1,385 | 1,385 | 1,385 |

가격·날짜·면적·층·준공연도·해제 상태를 포함한 공통 정규화 값은 전부 같았다. 상세 API의 공식 ID 보강 때문에 공통 거래 값이 틀어졌다는 증거는 이 범위에서 없다. 이 결과를 모든 과거 월의 가격 검증 완료로 확대하지 않는다.

일부 로컬 비교본과 현재 배포본의 값 차이는 현재 원천 정정과 구분해야 한다. 예를 들어 파크뷰 2026-05-13, 전용 124.515㎡, 22층은 로컬에 200,000만원이 있으나 현재 기본·상세 API 모두 222,000만원을 반환한다. 해당 차이는 상세 API 파서만의 가격 변환 오류로 설명되지 않는다. 계약 해제와 원천에서 사라진 행도 별도로 확인했다.

## 해결 방향

로컬에서 공식 단지 ID와 기존 확정 아파트의 연결을 대조·확정한 뒤, 공식 명령으로 기준본을 다시 생성해야 한다. 클라우드는 새 기준본을 설치하고 현재 수집 원천에서 조회 배정을 다시 만든다. 최신 클라우드 거래를 오래된 로컬 전체 DB로 덮어쓰지 않는다.

기준본 파일을 직접 편집하거나 GitHub에서 이름·주소 유사도로 공식 ID를 자동 승인하는 방식은 사용하지 않는다. 기본 API로 되돌리는 것만으로 공식 ID의 연결 이관이 완료되지는 않는다.

재발 검증에는 원천 건수·파일 해시 검사 외에 다음 조건이 필요하다. 같은 계약이 공식 ID 보강만으로 기존 조회 범위에서 사라지는지 확인하고, 사라질 경우 해당 공식 번호·원천 단지·영향받는 행을 배포 전에 보고한다. 알 수 없는 공식 번호는 기존 규칙대로 미확정 상태로 남기되, 승인된 단지의 조회 감소를 검사 통과로 숨기지 않는다.

이번 진단에서는 연결 확정·기준본 재생성·운영 코드 수정·수집·배포를 수행하지 않았다. 커밋과 푸시도 수행하지 않았다.
