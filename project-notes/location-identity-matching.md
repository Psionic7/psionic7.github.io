- [x] 공통 아파트 정보에 근거를 저장하고 실거래·매물 수집 경로에 적용한다.
- [x] 실제 미연결 자료를 재처리하고 남은 원인과 자료 보존 상태를 검사한다.

기준 상태는 커밋 `d1e1a69`다. 실거래 344,494행의 이름·주소 조합 612개 중 376개가 연결됐고, 기본 수집 범위 안 미연결은 8개, 범위 밖은 228개다. 매물 대상 464개 중 확인 성공 230개, 시간 초과 24개, 단지 검색 미확정 210개다.

## 판정 원칙

원본 이름·지번·거래 ID와 기존 아파트 ID를 보존한다. 위치는 후보를 찾는 데 사용하고, 가까운 점 하나만으로 다른 단지를 연결하지 않는다. 공식 식별자와 주소, 건물·필지 경계 및 차수의 근거를 기록한다. 자동 연결·모순·자료 부재를 구분하고 원본 자료가 화면과 검사 목록에서 사라지지 않도록 검증한다. 이번 작업은 커밋·푸시하지 않는다.

## 설계 비교 기준

1. 실제 8개 실거래 미연결과 매물 검색 누락을 근거와 함께 줄이는가.
2. 인접·동명·차수가 다른 단지의 잘못된 연결을 거부하는가.
3. 원천 좌표계·정확도·식별자와 원본 행을 추적할 수 있는가.
4. 기존 공통 ID, 수집 재실행, 데이터 추출·조회와 함께 동작하는가.
5. 추가 유료 서비스나 비공개 인증 정보 없이 재현할 수 있는가.

## 조사 근거와 선택

- [국토부 상세 실거래 API](https://www.data.go.kr/data/15126468/openapi.do)는 일반 API와 별도 서비스다. 현재 일반 API 원문에는 단지 일련번호·도로명 필드가 없으며 상세 API는 설정된 키로 HTTP 403이 반환됐다. 상세 API 보강은 선택 기능으로 분리한다.
- [주소기반산업지원서비스 API](https://business.juso.go.kr/jst/jstAddressApiList)는 주소·좌표 제공을 구분한다. 기존 저장 자료의 건물관리번호·공식 도로명 코드와 출입구 좌표를 보존해 사용한다.
- [국토부 GIS건물통합정보](https://www.data.go.kr/data/15123970/openapi.do)는 건물 공간정보와 건축물대장 속성을 건물 단위로 연계한다. 필지에 포함된 모든 도형을 특정 건물 하나의 경계로 간주하지 않는다.
- [K-apt 기본정보 API](https://www.data.go.kr/data/15058453/openapi.do)는 가입 단지를 대상으로 하므로 전체 주거 건물의 유일한 기준으로 쓰지 않는다.
- [Turf의 점-다각형 판정](https://turfjs.org/docs/api/booleanPointInPolygon)을 활용하되 좌표계·경계점·동일 출입구를 구분한다. 단순 최근접 거리나 이름 점수만으로 연결하지 않는다.

독립 설계 A/B 모두 원천 실거래 단지와 건물·주소 구획을 분리하는 방식에 수렴했다. B의 단일 정밀도 판정과 주소 구획 구조를 기준으로, A의 과거 거래 보존·전체 membership을 포함하는 상위 조회 규칙을 결합했다. 직접 행→대장 root만 연결하는 대안은 복합 root와 과거 동 미공개 행을 표현하지 못해 제외했다. 다른 모델 계열의 교차 심사 도구가 없어 심사는 수행하지 않았고, 두 설계안 전체를 같은 기준으로 직접 비교했다.

## 구현 계약

공통 진입점은 `server/apartment-identity.mjs`를 유지한다. `server/housing-identity.mjs`는 원천 단지·주소 구획·건물 membership·현재 거래 배정의 유일한 작성자다. 원래 실거래 컬럼과 대장 ID는 바꾸지 않는다. 월별 재수집으로 거래 ID가 바뀌면 배정도 재계산한다.

공유 선택 규칙은 `src/housing-identity.mjs`에 둔다.

```js
// 선택: 기존 root, 원천 단지, 건물/도로 구획
identity_ref = {kind: 'root' | 'source' | 'cohort', id: string}

// 원본 행당 배정 하나. 없는 정보는 채워 넣지 않는다.
identity = {
  entity_id: string,
  precision: 'building' | 'cohort' | 'complex' | 'unresolved',
  root_id: string | null,
  cohort_id: string | null,
  building_id: string | null
}
```

원천 단지 ID는 기존 지역·동·지번·원천 이름 튜플을 재사용한다. 구획 ID는 대장 root와 공식 도로명 주소키로 만든다. 선택 항목의 `identity_coverage.entity_ids`에는 그 선택이 전체 membership을 포함하는 원천 단지만 넣는다. 과거 complex 정밀도 행을 여러 하위 root에 중복 노출하지 않는다. 원천 단지 조회는 모든 원본 행을 한 번씩 보존한다.

일일 수집 대상은 `favorite` 외부에 `location`을 전달한다. 위치 문맥은 출처·좌표계를 가진 `anchors`, `primary_parcels`, 건물별 `roads`, 검증된 `parcels`다. 기대 위치를 네이버 관측 위치로 복사하지 않는다. 네이버의 실제 마커·단지 주소·좌표는 별도 관측 정보로 저장하고 공통 정책으로 검증한다.

공개 원천 실거래 JSON의 기존 필드는 유지한다. 조회용 월별 자료에는 배정을 함께 넣고, 공개 식별 catalog/SQL의 버전을 거래 자료와 함께 검증한다. `favoriteTradeMatches`, 선택 동일성, 검색·최근 N건·대시보드·주간 조회를 같은 선택 규칙으로 이관한다. 법적 연립·다세대·오피스텔 주거 건물은 원천 APT 분류와 실제 대장 용도를 따로 보존한다.

저장 매물의 공통 식별 참조 누락은 0개지만, 모든 대장 건물 연결이 확정됐다는 뜻은 아니다. 수지신봉현대빌라트는 원천 이름·지번과 실제 네이버 주소를 검증해 매매 광고 3건을 원천 ID에 연결했다. 실거래 102동과 대장 101동의 차이는 여전히 대장 검토 대상으로 남긴다. 매물 연결 검증과 대장 건물 확정을 분리한다. 오류 13개와 검색 미확정 68개는 매물 0건으로 표시하지 않는다. 지속 연결 구조와 재검사 방법은 [네이버 단지 연결 테이블](naver-persistent-matching.md)에 기록했다.

## 제공자 단지와 조회 범위 구분

네이버 단지 번호 하나가 여러 대장·주소 구획을 묶는 사례가 있다. 관측한 전체 광고는 보존하고, 같은 제공자 번호에 서로 구분되는 여러 공식 구획과 겹치지 않는 동 집합이 확인될 때만 해당 조회의 광고를 나눈다. 단순히 네이버의 동 표기가 한 대장과 다르다는 사실만으로 다른 단지라고 결론 내리지 않는다.

`identity_listing_members`는 구획별 동 목록과 `whole_cohort` 여부를 보존한다. `identity_reported_buildings`는 원천 실거래에서 공개한 동 목록이다. 원천 조회에는 대장에 확인된 동과 원천이 보고한 동을 함께 사용하되, 이를 대장 building 배정으로 바꾸지 않는다. 예를 들어 대진의 공식 102동 자료가 부족하더라도 원천이 보고한 102동의 매물까지 임의로 제거하지 않는다. 범위를 정확히 나누기 어려운 경우는 네이버 단지 전체 광고라는 안내와 함께 보존한다.

한 제공자 번호의 다른 주소 조회가 늦게 실패했다는 이유로 이미 성공한 전체 광고를 숨기지 않는다. 여러 선택을 API로 읽을 때는 공통 원본 관측을 반환하고 각각의 화면에서 범위를 적용한다. 선택 하나의 필터 결과로 다른 선택의 원본을 덮어쓰지 않는다.

저장한 선택 갱신은 지도용 목록 대신 공통 아파트 정보에서 수행한다. 동천센트럴자이에서 동 번호 없는 과거 거래 68건을 포함한 총 324건과 현재 매매 광고 191건을 실제 화면에서 대조했다. 아파트 정보 캐시와 통합 검색도 `manifest.housing.sha256` 버전을 함께 사용한다.

## 도로명주소 검색 실험

2026-11-08 PC 네이버 부동산의 실제 검색창에서 전체 주소 `경기도 용인시 수지구 고기로45번길 40-18`, 짧은 주소 `고기로45번길 40-18`, `신봉1로 121`을 시험했다. 단지 자동완성은 모두 없었다. 짧은 두 주소는 Enter 검색에서도 검색결과 없음이 표시됐고 해당 주소의 단지로 이동하지 않았다. 같은 세션에서 `동천센트럴자이`는 자동완성과 단지 112793 이동이 정상 동작했다.

## 재실행과 검증

```powershell
pnpm data:identities
pnpm listings:daily --retry-unresolved --source system-chrome --python ../insane-search/.venv/Scripts/python.exe
pnpm audit:matches --output local/data-validation/location-matches.json
pnpm test:data
pnpm data:export
pnpm data:verify
pnpm build
pnpm check:publish
```

GitHub Actions의 기존 일일 실거래 수집 작업도 같은 `collectDailyListings`와 공통 identity 재구성 경로를 사용한다. 위치 문맥을 서버의 대상에 전달하며 원천 거래·대장·주소·위치가 변경되면 기존 배정을 만료시킨다. 매물 수집의 명시적 접근 제한은 중단 상태로 유지한다. 이번 작업에서는 워크플로를 실행하거나 커밋·푸시하지 않았다.

공개 거래 원본은 바꾸지 않고 `data/housing-<hash>.json` sidecar로 배정을 배포한다. 거래 ID·원문 스냅샷·행 수·체크섬을 검증하며, 월별 조회와 검색은 같은 sidecar 버전을 사용한다. 검사 결과는 `local/data-validation/location-matches.json`과 동명의 Markdown, `local/location-*-tests.log`에 남긴다.
