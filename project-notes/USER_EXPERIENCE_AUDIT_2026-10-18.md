## 결론과 요약

첫 방문에서 전체 실거래 자료를 내려받지는 않는다. 공개 사이트의 기본 첫 화면은 약 **0.41MB**, 한 동의 한 달 거래 조회는 약 **0.48MB**였다. 월별로 필요한 자료만 받는 현재 구조는 유지할 가치가 있다.

## 2. 검색: 용량은 작지만 실제 거래가 있는 단지가 누락된다

### 확인된 문제

첫 화면 검색은 `/apartment-map/apartments-*.json`에 들어 있는 **467개 지도 단지**를 검색한다. 반면 지역별 실거래 카탈로그에는 **아파트명·동·지번 조합 612개**가 있다. 서로 같은 단지의 과거 명칭·별칭·필지가 있을 수 있으므로 612를 실제 단지 수로 볼 수는 없다.

지도 단지의 `trade_keys` 또는 기본 키와 대조했을 때 **253개 거래 키가 직접 연결되지 않았다**. 이것도 253개의 실제 단지가 모두 누락됐다는 뜻은 아니다. 그러나 다음은 실제 브라우저에서 누락이 재현됐다.

| 검색어 | 거래 카탈로그에 존재 | 첫 화면 단지 검색 결과 |
|---|---|---:|
| 벽적골우성 | 영통동 973-3 | 0건 |
| 주공그린빌3 | 매탄동 1277 | 0건 |

사용자는 “실거래가가 없다” 또는 “이 사이트에 자료가 없다”고 오해할 수 있다. 상세 조회 조건에서 지역을 선택해 거래 카탈로그로 찾는 경로가 있어도, 통합 검색의 0건 결과는 사용자의 다음 행동을 막는다.

### 개선 방향

실거래 카탈로그를 검색 기준으로 삼고 지도 단지 정보를 연결하는 편이 적절하다. 좌표·지도 경계가 없어도 실거래 검색은 가능해야 한다. 별칭·이전 명칭·지번을 정규화하고 중복 후보는 명확하게 표시한다. 검색 목록에는 최근 거래일이나 “선택 기간 거래 없음”도 도움 된다.

첫 검색은 압축 약 50KB 추가여서 부담이 작다. 다만 검색어를 지웠다가 다시 입력하면 검색 목록을 다시 요청·파싱하는 구조다. HTTP 캐시로 회선 비용은 줄지만 공통 인덱스의 메모리 캐시를 두면 반복 처리도 줄일 수 있다. 매 키 입력마다 전체 거래 파일을 다운로드하는 구조는 아니다.

## 3. 아파트 지도: 가장 큰 성능 개선 대상

### 다운로드 문제

- 경계 GeoJSON 원본: **10,442,539바이트**. 로컬 gzip 계산 약 2.435MB. 실제 공개 사이트의 압축 전송량은 압축 설정과 응답 헤더 때문에 다를 수 있다.
- 검색용 단지 목록 원본: **548,637바이트**. 로컬 gzip 약 45KB.
- `loadApartmentMap()`은 단지 목록과 경계를 함께 받은 뒤, 모든 좌표와 연결을 검증하고 나서 지도를 보여준다.
- 낮은 확대 수준에서 동별 숫자 묶음만 보거나, 단지 목록만 보거나, 경계 표시를 끄더라도 최초에 경계 전체를 받는다. 표시 옵션이 다운로드 양을 줄여 주지는 않는다.
- 모바일 실측은 JS 힙 약 **95MiB**, 큰 작업의 50ms 초과분 합계 약 **3.9초**였다. 이는 브라우저 전체 메모리나 공식 TBT/INP 값은 아니다. JSON 파싱·검증·레이어 생성 등 복합 비용을 포함하며 각 비용을 분리 프로파일링한 결과는 아니다.

### 확대·조작 문제

동별 숫자 묶음을 눌러 확대 14로 들어가자 SVG 경로가 **3개 → 9,397개**, 페이지 DOM이 약 **640개 → 11,394개**로 증가했다. 해당 PC 조작은 약 2.80초 후 대상 마커가 표시됐다. 보충 측정의 50ms 초과 작업 합계는 약 0.47초였다.

`ApartmentMapCanvas`는 확대 14 이상에서 선택된 단지 전체와 연결된 경계를 생성하며, 현재 화면에 들어오는 경계만 고르는 처리가 없다. 원본 경계 feature는 8,928개이고, 여러 Polygon 등의 표현 때문에 실제 SVG path 수와 같지 않다. 지도에 보이지 않는 곳도 그리기 대상으로 만들어져 저사양 휴대전화의 확대·이동·필터 변경에서 부담이 커질 수 있다.

### 우선 개선

1. 목록과 중심점만 먼저 표시하고 상세 경계는 실제 필요한 시점에 받는다.
2. 경계를 시군구/동 또는 공간 타일로 분할하고 현재 지도 영역만 로드·표시한다.
3. 낮은 확대에는 단순화한 경계, 높은 확대에는 상세 도형을 쓴다.
4. 화면 밖 레이어를 제거하고, 사용한 데이터와 검증 결과를 제한적으로 재사용한다.
5. Canvas 전환만으로 다운로드·파싱 문제가 해결되지는 않는다. 공간 분할과 화면 범위 제한을 먼저 적용하고 렌더러 선택은 이후 비교한다.
6. 점 표시·목록 조회·즐겨찾기는 경계 수신 실패와 독립적으로 동작하도록 만든다.

지도 탭 재진입은 캐시가 있는 PC 보충 측정에서 약 0.61초였다. HTTP 캐시는 효과가 있지만 소스상 재파싱·검증·지도 재구성은 다시 발생한다. 한 번의 힙 스냅샷 증가만으로 메모리 누수를 판정하지는 않았다.

## 4. 거래 조회: 현재 분할 구조는 적절하다

- 시군구별·월별 JSON만 요청하며, 한 시군구를 여러 동/단지가 공유하면 같은 월 데이터는 재사용한다.
- 선택 아파트 한 곳만 조회해도 해당 시군구·해당 월의 거래를 받은 다음 브라우저에서 걸러낸다. 현재 표본에서는 추가 약 30KB였으므로 당장 단지별 API 서버로 바꿀 근거는 부족하다.
- 월 파일은 한 시군구에서 최대 6개씩 묶어 요청한다. 여러 시군구를 동시에 조회하면 총 병렬 요청은 6개보다 많을 수 있다.
- 1년·여러 해를 선택하면 해당 기간 월 자료가 늘어난다. 화면의 페이지당 50건은 DOM을 제한하며, 다운로드를 50건으로 제한하는 서버 페이지네이션은 아니다.
- 기본 동/단지 거래표가 같은 컴포넌트를 사용한다. 계약일 단축 표기, 상태/해제일, 면적 단위, 억 원 표시가 일관적이다.
- 지연 응답이 최신 조회를 덮어쓰지 않도록 되어 있고 실패한 지역은 따로 재시도할 수 있다.
- 전역 월 자료 캐시에 제거 한도가 없다. 장시간 여러 지역·여러 해를 탐색하면 받은 자료를 계속 보유할 수 있다. 현재 짧은 흐름에서 힙은 대략 4~14MiB였지만 장기 누적은 별도 관리하는 편이 좋다.
- 조회를 바꿔도 기존 HTTP 요청을 중단하지는 않는다. 취소 처리는 공유 중인 요청을 끊지 않도록 설계해야 한다.
- `fetch`에 명시적 시간 제한이 없어 회선이 멈춘 경우 브라우저가 실패를 확정할 때까지 로딩 안내에 머무를 수 있다.

## 5. 모바일: 가로 넘침보다 스크롤과 정보 도달 시간이 문제

### 확인한 장점

- 390px와 320px에서 문서 전체의 가로 넘침이 없었다.
- 모바일 거래는 카드 형태로 바뀌어 가격·날짜·면적·층을 좌우로 밀지 않고 읽을 수 있다.
- 하단 주요 메뉴, 접는 필터, 조회 선택 요약, 지도/목록 전환이 있다.
- 입력창 크기, 주요 버튼 이름, `aria-expanded`, 본문 건너뛰기, 패널 접기 등 기본 조작 장치가 있다.

### 개선할 점

- 풍덕천동 9월 거래 50건을 표시한 320×720 화면의 문서 높이는 **12,282 CSS px**였다. 화면 높이의 약 17배이며, 고정 메뉴를 빼면 실질적으로 더 많이 스크롤해야 한다.
- 그 화면에서 첫 거래 가격은 처음 보이는 영역의 맨 아래, 하단 메뉴 뒤쪽에 걸쳐 있었다. 스크롤하면 읽을 수 있지만 조회 결과에 도달하는 데 헤더·자료 안내·탐색 메뉴·선택·기간 도구가 많은 공간을 차지한다.
- 모바일에서 20건/더 보기, 거래 카드 간격 조정, 결과로 이동, 다음 페이지 후 결과 시작으로 이동 등을 검토할 만하다. 비교를 위해 필요한 날짜·면적·층·거래 상태는 유지한다.
- 키보드로 검색어를 입력했을 때 결과 첫 항목으로 자연스럽게 이동하는 전용 검색 키보드 조작은 소스상 별도 구현이 없다. 일반 Tab과 버튼 선택은 가능하지만 검색 상자에 자동완성 목록 수준의 방향키 경험은 제공하지 않는다.
- 검색어와 결과 수가 바뀌고 폰트가 교체될 때 배치가 움직인다. 320px 거래 페이지의 무입력 로딩에서 세 번의 유효 이동 합계이자 한 세션 구간의 값은 약 **0.172**였다. 다른 주 측정의 단순 이동 누적 합계를 공식 CLS로 사용하지 않았다.

측정한 화면의 보이는 일반 버튼에서 24px 미만 크기와 이름 없는 버튼은 검출되지 않았다. 지도 도형, 색 대비, 모든 초점 경로, 200% 확대, 실제 스크린리더까지 검증한 것은 아니므로 접근성 적합 판정으로 확대 해석할 수 없다. 지도 외에 목록으로 같은 목적을 달성할 수 있는 점은 장점이다.

## 6. 데이터의 범위·정확성·갱신을 사용자가 이해할 수 있는가

- 공개 거래 자료: **343,543건**, **수원시 영통구·성남시 분당구·용인시 수지구**, manifest의 수집 동 이름 합계 **26개**.
- 지역 카탈로그 1,215개가 모두 실거래 수집 대상이라는 뜻은 아니다. 지역 지도는 거래 제공/미수집 상태를 구분하고 거래 조회에서는 제공 지역 중심으로 선택하게 하는 점이 좋다.
- 지도 마스터는 467개, 좌표 466개, 위치 미확인 1개, 명칭 미확인 7개다. 지도 수집 상태가 있는 동은 21개이며 `coverage.complete=false`다. **지도 수집 범위와 거래 수집 범위가 다르다.** 이것이 검색 인덱스를 지도에만 의존하면 안 되는 또 다른 이유다.
- 공개 파일의 게시 시각: `2026-10-17T18:03:54.339Z` = **2026-10-18 03:03:54 KST**. 화면 기준일도 10월 18일이었다. 공개 데이터가 15일 뒤처졌다고 판단할 근거는 없다.
- 로컬 파일은 `2026-10-03T13:45:18.472Z`, 343,038건이었다. 로컬/공개 자료를 구분하지 않으면 잘못된 지연 진단이 나온다.
- 수집 워크플로의 cron은 UTC 16:00, KST **01:00 1회**다. 수집 시작 예정 시각과 공개 파일 게시 완료 시각은 다르다. 원천 API의 모든 거래가 언제 반영됐는지는 게시 시각만으로 알 수 없다.
- 화면에 기준일·지연 안내, 신고 지연·해제·정정 설명이 있고, 미수집/실패/거래 없음도 구분한다. 이 구조는 유지하는 것이 좋다.
- 장시간 열어 둔 탭은 manifest를 주기적으로 재확인하지 않는다. 다음 날에도 과거 게시 자료가 남을 수 있다. 화면 복귀 시 새 자료 알림 또는 명시적인 새로고침 기능을 검토한다.
- 새 단지를 선택하면 기본 기간에 거래가 없을 수 있다. “기간을 늘려 보세요” 외에 최근 거래일과 “최근 90일 보기” 동작이 있으면 빈 화면에서 빠져나오기 쉽다. 임의로 기간을 바꾸고 사용자에게 알리지 않는 방식은 피한다.
- 면적은 ㎡/전용평이며 공급면적·분양 평형과 다르다는 설명이 있다. 같은 전용면적 흐름은 해제 거래를 제외하고 층·향 차이는 보정하지 않았다고 설명한다. 가격 차이를 곧바로 시세 변동으로 단정하지 않게 해 주는 장점이다.
- 지역 경계 기준은 2023-07-29이며 안내에도 표시된다. 현재 행정구역과 다를 가능성을 사용자에게 계속 알려야 한다. 이번에 각 법정동 개편 내역을 일일이 대조한 것은 아니다.
- 원천 API와 거래 행 전체의 수치 일치 여부는 이번 성능/사용성 진단에서 전수 대조하지 않았다.

## 7. 즐겨찾기: 사용은 간단하지만 보관 신뢰성에 보완 필요

- 동/단지 즐겨찾기는 브라우저 localStorage에 저장한다. 로그인 없이 빠르게 저장할 수 있고, 공유받은 목록이 내 목록을 덮어쓰지 않는다.
- “현재 브라우저에 자동 저장” 안내가 있다. 다만 PC→휴대전화, 다른 브라우저, 시크릿 창 사이의 자동 동기화는 없다. 사이트 데이터 삭제나 브라우저 초기화 때 사라질 수 있다.
- 전체 삭제는 확인·되돌리기가 있고 조회 설정 초기화와 즐겨찾기 삭제를 나누어 안전하다.
- `localStorage.setItem` 실패를 조용히 무시한다. 저장이 차단되거나 용량이 부족하면 화면에서는 선택이 바뀌어도 다음 접속에 남지 않을 수 있다. 저장 실패를 알리는 표시가 필요하다.

### 재현한 저장 한도 결함

`readDocument()`는 저장 문자열이 **262,144자보다 길면 빈 문서로 취급**한다. 반면 저장 함수에는 같은 크기 제한이나 경고가 없다.

사용자의 브라우저와 분리한 가짜 localStorage에서 현재 467개 실제 단지 객체로 확인했다.

- 즐겨찾기만 467개: 약 132,079자, 정상 복원.
- 즐겨찾기와 조회 선택에 같은 목록을 함께 보관: 시험 순서에서 **464개, 262,425자**부터 즐겨찾기를 0개로 읽음.
- 그 상태에서 일반 표시 설정을 저장하면 기존 문서 대신 새 작은 문서가 쓰여 실제 목록도 사라짐.

이는 **대량 선택 조건에서 실제 재현된 결함**이다. 보통 몇 개를 저장하는 사용자가 바로 겪는 문제로 과장하면 안 된다. 그러나 허용 개수는 1,000개인데 저장 크기와 일치하지 않으므로 조기에 고칠 가치가 있다. 식별자 중심 저장, 공통 객체 중복 제거, 초과 시 기존 값 보존, 저장 실패 알림, 백업 내보내기/가져오기 등을 검토한다.

다중 탭의 `storage` 이벤트 동기화는 확인되지 않았다. 여러 탭에서 같은 설정을 바꾸면 뒤에 저장한 이전 상태가 다른 변경을 덮을 가능성이 있다. 이 부분은 소스 기반 가능성이고 이번에 탭 간 충돌을 재현한 것은 아니다.

## 8. 오류·불안정한 회선·오프라인

- 기본 자료 목록을 의도적으로 HTTP 503으로 막았을 때 오류·재시도 버튼이 나타났다. 차단 해제 후 다시 불러오기로 정상 복구했다.
- 검색 목록을 503으로 막았을 때 실패 안내·다시 시도가 나타났고, 차단 해제 후 검색 결과가 복구됐다.
- 정상 주요 흐름 19개와 보충 흐름에서 예상 밖 JavaScript 페이지 오류나 HTTP 실패는 관찰되지 않았다. 오류 주입 2건은 의도된 실패다.
- 지도 경계 실패 시 재시도는 있지만 현재 지도 목록도 전체 경계 로딩에 묶여 있다. 경계가 실패해도 목록·점·거래 조회는 계속 쓰게 하는 편이 좋다.
- 지도 타일 실패 안내가 있으나 어떤 타일 하나가 성공하면 오류 상태를 지우는 구조라 부분 실패 안내가 충분히 유지되지 않을 가능성이 있다. 이는 소스 분석이며 실제 타일 장애를 이번에 주입하지 않았다.
- Service Worker 기반 오프라인 보장은 없다. 캐시된 일부 자산은 남아도 첫 manifest가 실패하면 초기 화면에서 막힐 수 있다. 오프라인 전체 지원은 현재 사이트 목적상 최우선 과제는 아니다.
- 데이터 배포 중 파일 버전 불일치나 lazy chunk 교체 실패는 이번에 재현하지 않았다. 해시 파일 보존과 화면 재로딩 안내를 회귀 점검하는 정도가 합리적이다.

## 9. 공유·뒤로가기·개인정보·접근 경로

- 조회 조건을 주소에 넣고 뒤로가기·화면 전환·스크롤 복원을 지원한다. 주소 복사 실패 때 수동 복사 대체도 있다.
- 단지 선택 객체 전체가 주소의 `apt`에 JSON으로 들어간다. 여러 단지를 비교하면 주소가 길어지고 메신저 공유가 불편해질 수 있다. 식별자로 줄이고 오래된 링크를 복원할 카탈로그가 필요하다. 대량 URL 제한은 이번에 별도 재현하지 않았다.
- 관심 목록 공유 주소에는 사용자가 선택한 동/아파트가 포함된다. 비밀번호 같은 비밀 정보는 아니지만 관심 지역이 공유 상대와 URL에 드러난다. 공유 범위를 짧게 알려 주면 더 명확하다.
- 분석 범위에서 별도 사용자 계정 수집이나 분석 SDK는 발견하지 못했다. Google Fonts와 OpenStreetMap 타일로 외부 요청이 나가며, 이 서비스는 방문 IP·요청 정보를 받을 수 있다. 외부 요청 자체가 없다고 안내해서는 안 된다.
- 로그인·유료 서비스·원천 API 키를 일반 방문자가 입력할 필요가 없다. 관리자 화면 인증은 별도 경로이며 이번에 관리자 자격 증명이나 원천 API 비밀값을 사용하지 않았다.
- 원본 HTML은 React 루트와 공통 title/description 중심이다. 페이지 내용과 상세 제목은 JS 실행 후 만들어지고, 단지별 Open Graph·canonical·서버 HTML은 확인되지 않았다. 특정 단지 링크의 검색 노출·메신저 미리보기 개선에는 여지가 있다. 현재 검색 순위나 색인 실패를 실제 검증한 것은 아니다.
- SEO만을 위해 전체 사이트를 즉시 다른 프레임워크로 옮길 필요는 없다. 주요 단지의 사전 생성 페이지를 필요에 따라 검토한다.
