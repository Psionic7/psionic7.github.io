# 아파트 공통 정보 아키텍처와 구현 인계 계획

작성일: 2026-11-10. 상태: **사용자 승인 후 구현·실데이터 검증 완료**.

이후 작업의 소유권·원천 저장·ID 기준은 [데이터 소유권과 공급자 단지 ID 운영 규칙](data-ownership-and-provider-identities.md)을 우선한다. 로컬 확정 아파트·연결표, 네이버 매물 저장 영역, 실거래 저장 영역을 분리하고 공급자 공식 단지 ID로 연결한다. 아래 기존 구현의 이름·주소 기반 source 키를 공식 단지번호로 간주하지 않는다.

이 문서의 구현 검증은 로컬 작업 DB 기준이다. 이후 실제 배포 조사에서 로컬 확정 아파트 정보보다 클라우드 복원 DB의 옛 아파트 정보가 우선돼 부속시설이 다시 지도에 나타나는 차이를 확인했다. 아파트 원천은 로컬, 실거래·네이버 매매 매물 수집은 GitHub라는 소유 범위를 유지해야 한다. 현재 실서비스 상태와 후속 해결안은 [데이터 미매칭 보고서](apartment-data-matching-report-2026-11-10.md)를 먼저 확인한다.

사용자는 설계와 인계 문서 작성 이후 “구현해”로 구현을 승인했다. 아래 설계·실행 계획은 결정 근거로 유지하고, 실제 구현 결과와 재실행 방법은 마지막의 **구현 기록**에 정리한다. 커밋·푸시·배포는 이번 구현 요청에 포함되지 않는다.

구현에서는 기존 미커밋 즐겨찾기 수정을 보존했다. 작업 DB를 SQLite 백업 API로 백업하고 복사본에서 재구성·추출·검색 검증을 먼저 통과한 뒤 원본 작업 DB에 적용했다. 아래의 구현 전 진단 수치는 이관 전 기록이며 현재 지도 수와 구분한다.

현재 사용 방법은 [아파트 식별 정보 통합](apartment-identity.md), 구현 전 원인 분석은 [2026-11-10 진단 근거](apartment-information-evidence-2026-11-10.json)를 함께 참조한다. 아래 '예정', '승인 후' 표현은 승인 당시 계획의 기록이다.

## 권장 결정

기존 `apartment_identity`를 단지 마스터로 유지하고, 위치·구역·주거동 판정·조회 범위를 하나의 `apartment_information` 통합 조회 뷰와 공통 API로 제공한다. 지도, 검색, 즐겨찾기, 실거래, 매물 연결은 이 공통 정보의 식별자와 판정 결과를 사용한다.

출입구, 건물, 주소 구역, 필지는 한 단지에 여러 개가 있다. 기존 원천 관계 테이블은 이 관계와 관측 근거를 보존한다. 앱이 이 테이블들을 직접 조합해 단지를 다시 판단하는 경로를 제거한다. 큰 경계 도형은 공통 정보가 지정한 구역 참조로 조회하고, 브라우저에는 필요할 때 내려준다.

여기서 ‘하나로 판단’은 모든 기능이 동일한 조회 결과와 동일한 식별자를 사용한다는 뜻이다. 물리적으로 원천 테이블을 하나로 합치면 여러 출입구와 구역을 중복 저장하거나 잃게 된다. 단지 마스터와 여러 구역의 관계를 보존하면서 앱의 조회 기준을 하나로 만드는 구성이 적합하다.

## 현재 문제와 설계 제약

- `apartmentInformation()`은 주로 이름과 주소를 제공한다. `masterMapData()`는 좌표, 필지, 외곽선, 용도지역과 즐겨찾기 값을 별도로 조합한다.
- 지도 항목에는 명시적 `identity_ref`가 없다. 지도에서 저장한 root가 즐겨찾기 갱신 중 cohort로 바뀌어 별표와 즐겨찾기 필터에서 누락된다.
- 상록마을의 경비실과 지하주차장은 실제 용도가 부속시설인데 층별 용도 코드 때문에 아파트로 분류됐다.
- 단지 전체(root), 주소 구역(cohort), 실거래 원천(source)은 조회 범위가 다르다. 이를 이름이나 `master_id`만으로 같은 선택으로 취급해서는 안 된다.
- 같은 필지나 출입구를 공유하는 사실은 같은 아파트라는 증거가 아니다. 검증되지 않은 연결과 과거 원천 거래의 전체 조회 경로를 보존해야 한다.

## 대안 비교

| 구성 | 장점 | 비용과 한계 | 결정 |
| --- | --- | --- | --- |
| 기존 단지 마스터와 공간 관계를 통합 조회 뷰로 제공 | 기존 ID를 보존하고 공간 자료 중복을 줄인다. 판단 코드와 공개 카탈로그를 한곳에 둔다. | 기존 호출부와 공개 자료 생성 경로를 함께 이관해야 한다. | 권장 |
| root·cohort·source별 새 물리 테이블을 만들고 전체 정보를 복제 | 선택 단위로 SQL 조회하기 쉽다. | 기존 마스터와 새 테이블 사이에 추가 동기화, 무효화, 갱신 순서가 필요하다. | 현재는 도입하지 않는다. |
| 단지 한 행에 모든 좌표·건물·도형을 큰 JSON으로 저장 | 한 행만 읽으면 전체 자료를 얻는다. | 공유 도형을 반복 저장하고 작은 변경에도 큰 값을 다시 쓴다. 관계와 범위 검증도 어려워진다. | 채택하지 않는다. |

공간 원천은 정규화해 유지하고, 공통 조회 결과와 공개 카탈로그를 하나로 만든다. 별도의 선택별 복제 테이블은 직접 SQL로 모든 범위를 조회할 필요가 추가로 확인될 때 재검토한다.

## 저장 구조와 소유권

### 1. 단지 마스터: `apartment_identity`

기존 `apartment_id`와 대장 ID를 유지한다. 이름, 주소, 별칭, 우편번호와 기존 제공자 연결의 근거도 유지한다. 다음 판정 값을 공통 정보에서 관리한다.

| 항목 | 의미 |
| --- | --- |
| `apartment_id` | 기존 단지 ID. 이름이나 주소 변경으로 새 ID를 만들지 않는다. |
| `residential_status` | 확인된 주거 단지, 부속시설만 있는 항목, 판단 보류를 구분한다. |
| 대표 위치 참조 | 검증된 건물과 출입구를 가리킨다. 좌표 원천과 중복된 좌표 사본을 각 기능이 따로 유지하지 않는다. |
| 공간 자료 버전 | 위치·구역 자료가 어느 관측과 생성 버전에 속하는지 확인한다. |
| 판정 근거와 확인 시각 | 주거 여부, 위치, 연결 판단을 추적하고 재검토할 때 사용한다. |

좌표 값은 통합 뷰가 대표 위치 참조를 통해 반환한다. 좌표가 없으면 `NULL`과 미확인 상태를 반환한다. 경계 중심점을 실제 관측 좌표로 저장하지 않는다.

### 2. 위치와 구역 관계

기존 테이블의 역할을 명확히 하고 중복 테이블 생성을 최소화한다.

| 기존 관계 | 역할 |
| --- | --- |
| `apartment_buildings`, `apartment_building_inventory` | 실제 건물, 주거동과 부속시설, 법정동, 주소와 분류 근거 |
| `apartment_entrances` | 건물별 관측 출입구와 좌표, 출처, 관측 시각 |
| `housing_identity_cohorts` | 한 단지 안의 주소 구역과 해당 건물 집합 |
| `apartment_parcels` | 주필지와 부속 필지, 경계 확인 상태와 도형 |
| `apartment_footprint_links`, `apartment_building_footprints` | 건물 외곽선과 그 연결 근거 |
| `apartment_zoning_links`, `apartment_zoning_features` | 용도지역과 해당 공간 자료 |
| `housing_identity_entities`, `housing_identity_members`, `housing_identity_bindings` | 원천 실거래 단지, 검증된 구역 연결, 거래별 유일한 배정 |

공간 조회와 검증 정책은 `server/apartment-identity.mjs`가 소유한다. 세부 공간 조립 코드는 내부 모듈로 분리할 수 있지만, 외부 호출부가 그 내부 모듈이나 원천 테이블을 사용해 단지를 다시 판단하지 않게 한다.

### 3. 통합 조회: `apartment_information`

통합 조회 결과의 단위는 ‘선택 범위’다. 기존 root만 읽는 호출부는 root를 명시하고, 지도·검색·거래는 필요한 범위의 같은 계약을 사용한다. 구현 시 기존 root 조회 뷰를 이 계약으로 확장한다.

| 필드 묶음 | 반환 정보 |
| --- | --- |
| 식별 | `selection_id`, `scope_kind`, 단지 ID와 명시적 상위·하위 참조 |
| 기본 정보 | 대표 이름, 검증된 별칭, 지번과 도로명주소, 우편번호 |
| 주거 판정 | 주거 상태, 활성 상태, 지도 선택 가능 여부와 사유 |
| 위치 | 대표 좌표, 위치 정밀도, 관련 출입구 참조, 확인 상태, 출처와 관측 시각 |
| 구역 | 법정동과 행정구역, 주소 구역, 주필지·부속 필지, 경계·외곽선·용도지역 참조 |
| 조회 범위 | `identity_ref`, 거래 포함 범위, 과거 원천 거래 경로, 매물 연결 범위 |
| 버전 | 식별 자료와 공간 자료 버전, 스키마 버전 |

`selection_id`와 `scope_kind`가 선택을 식별한다. source가 아직 단지에 연결되지 않았다면 임의의 단지 ID를 배정하지 않고 미확정 관계를 반환한다.

대표 위치를 반환해도 모든 동과 구역의 위치를 하나로 덮어쓰지 않는다. 구역을 선택하면 해당 건물의 출입구와 필지 관계를 사용한다. 단지 전체에만 연결된 외곽선은 구역 전용 경계로 표시하지 않는다.

## 읽기와 생성 계약

기존 `apartmentInformation`, `searchApartmentInformation`, `resolveApartmentIdentity`를 공통 진입점으로 유지하고 범위와 공간 정보 옵션을 명시한다. 원천 증거를 읽는 내부 경로와 앱이 검증된 정보를 읽는 경로를 모듈 내부에서 분리한다. 재구성 중인 결과를 재구성 입력으로 읽는 순환을 방지한다.

공개 자료는 이 공통 결과에서 생성한다.

```text
검증된 대장·주소·출입구·필지·거래 원천
                    ↓
        주거 판정 + 식별 관계 재구성
                    ↓
 apartment_identity + 기존 위치·구역 관계
                    ↓
      apartment_information / 공통 API
                    ↓
          버전이 있는 공통 공개 카탈로그
           ↙           ↓            ↘
       지도 자료     검색 자료     거래·매물 조회
                    ↓
             같은 참조의 즐겨찾기
```

- `masterMapData()`의 별도 단지 조합 로직을 제거한다. 지도 항목은 공통 카탈로그의 식별자·이름·위치·범위를 그대로 투영한다.
- 검색 자료를 만들 때 지도 자료와 공통 자료를 합쳐 이름이나 ID를 보완하던 경로를 제거한다.
- 공개 카탈로그에는 위치와 구역 요약을 넣는다. 큰 도형은 공통 구역 ID와 버전으로 검증되는 경계 파일과 지도 조각으로 제공한다.
- 지도 조각은 전송 형식이다. 조각 생성이나 화면 코드에서 새로운 단지 연결 정책을 만들지 않는다.
- 카탈로그 자체의 체크섬을 버전으로 사용한다. 거래 배정이 같아도 공간 자료가 바뀌면 지도·검색·캐시가 갱신돼야 한다.
- 지도, 검색, 거래 배정, 공통 카탈로그의 참조와 버전이 어긋나면 게시 검증을 실패시킨다.

## 판단 규칙

1. 식별자와 범위를 먼저 사용한다. 이름, 같은 주소, 가까운 좌표만으로 단지를 합치지 않는다.
2. 주거 판정에는 실제 용도와 주거층 근거를 사용한다. 아파트 용도 코드만 가진 주차장·경비실은 주거동으로 분류하지 않는다.
3. 세대수 0만으로 부속시설을 판정하지 않는다. 노인복지주택의 호수, 복합건물의 실제 주거층, 미확인 값을 구분한다.
4. 부속시설은 원천과 연결 근거를 보존하되 일반 아파트 선택 목록에서 제외한다. 연결할 부모 단지가 미확정이면 임의로 이웃 단지에 합치지 않는다.
5. 위치 미확인, 구역 경계 미확인, 단지 연결 미확정은 별도 상태다. 이를 거래 0건과 같은 뜻으로 취급하지 않는다.
6. 거래 ID마다 배정은 하나다. 과거 공유 거래를 모든 하위 구역에 복사하지 않는다.
7. 공간 정보의 포함 관계와 선택의 동일성은 구분한다. 지도 강조나 즐겨찾기 표시가 상위·하위 관계를 사용하더라도 실제 조회는 저장된 정확한 범위를 유지한다.

## 기존 즐겨찾기 처리

- 새 지도 항목은 처음부터 공통 카탈로그의 명시적 `identity_ref`를 사용한다. 저장 직후 메타데이터를 불러와도 ID가 바뀌지 않는다.
- 기존의 명시적 root, cohort, source 선택은 원래 조회 범위를 보존한다.
- 구형 저장값은 공통 정보에 근거한 변환 규칙으로만 이관한다. 다중 주소 구역을 통째로 같은 단지 선택으로 바꾸지 않는다.
- 이미 cohort로 저장된 값도 지도에서 인식할 수 있게 공통 구역 관계를 사용한다. 이를 해결하려고 일반 식별자 비교를 `master_id` 비교로 완화하지 않는다.
- 잘못 노출됐던 부속시설의 즐겨찾기는 정상 아파트로 임의 이전하지 않는다. 공통 정보의 상태와 확인 경로를 표시한다.
- 즐겨찾기와 공유 주소에는 식별자와 필요한 조회 범위만 저장한다. 좌표, 경계 도형, 출입구 목록과 공간 근거는 복사하지 않는다.
- 현재 `refreshApartmentFavorites()`가 최신 행 전체를 복사하는 부분은 작은 선택 정보만 복사하게 바꾼다.

## 승인 후 구현 순서

| 단계 | 작업 | 단계 완료 기준 |
| --- | --- | --- |
| 1. 기준 확보 | 작업 DB 백업, 원본 거래 ID·건수·해시와 현재 선택 범위를 기록한다. 상록마을 실패를 테스트로 고정한다. | 복구 경로와 실패 원인이 확인된다. |
| 2. 공통 정보 모델 | 마스터 확장, 위치·구역 조회 계약, 분류와 출처 상태, 통합 뷰와 공통 API를 구현한다. | 동일 입력으로 반복 재구성해도 결과가 같다. |
| 3. 호출부 이관 | 지도·검색·즐겨찾기·거래·매물 연결을 공통 정보로 이관하고 별도 조합 경로를 제거한다. | 모든 공개 지도 ID와 범위가 공통 카탈로그와 일치한다. |
| 4. 데이터 재구성 | 기존 원천으로 대장 분류, 공통 정보, 거래 배정과 공개 자료를 공식 명령으로 재구성한다. | 원본 거래를 보존하고 부속시설 선택 오류가 사라진다. |
| 5. 검증·미리보기 | 회귀 검사, 원본 DB 대조, 게시 검사, 모바일 동작 확인을 수행하고 로컬 화면을 연다. | 아래 수용 기준을 충족하고 결과를 보고한다. |

갱신 순서는 원천 분류 → 공통 기본·공간 정보 → 거래 관계와 배정 → 공통 공개 카탈로그 → 지도·검색 자료다. 현재 `apartment_identity` UPDATE는 주거 배정을 무효화한다. 따라서 배정 생성 후 다시 아파트 정보를 쓰는 순환을 만들지 않는다. 버전이 섞인 중간 결과를 게시하지 않는다.

## 수용 기준

- 상록우성, 라이프1차, 라이프2차, 임광·보성의 실제 데이터에서 지도 저장, 해제, 즐겨찾기만 보기, 새로고침과 거래 조회가 일치한다.
- 주차장과 경비실만 있는 두 상록마을 항목이 일반 아파트 선택에서 제외된다. 해당 대장과 도형 원천은 보존된다.
- 같은 이름의 다른 단지, 같은 주소를 공유한 대장, 한 단지 안의 여러 주소 구역을 잘못 합치지 않는다.
- 미배정 과거 거래의 원천 전체 조회 경로가 유지된다. 원본 ID마다 배정은 정확히 하나다.
- 좌표가 없는 단지와 미확인 경계를 확인된 것처럼 표시하지 않는다.
- 공통 정보 변경 후 지도·검색 자료와 브라우저 캐시가 같은 버전을 사용한다.
- 즐겨찾기 저장값과 공유 URL에 공간 도형이나 좌표가 들어가지 않는다.
- 필수 검사: `pnpm test:data`, `pnpm audit:matches --output local/data-validation/apartment-matches.json`, `pnpm data:identities`, `pnpm data:export`, `pnpm data:verify`, `pnpm build`, `pnpm check:publish`, 관련 식별·지도·즐겨찾기 테스트.
- 모바일 Chrome 터치 환경에서 실제 원천 기반 흐름을 검사한다. 아이폰 실기기 연결이 없으면 그 검증 한계를 구분해 보고한다.

## 승인 범위

이 설계 승인은 스키마와 공통 API 변경, 호출부 이관, 백업 후 로컬 데이터 재구성, 테스트와 로컬 미리보기를 포함한다. 커밋, 푸시와 외부 배포는 별도 명령이 있을 때 진행한다. 현재는 승인 대기 상태다.

## 2. 상록마을 원인과 보존할 회귀 자료

관찰 범위는 경기도 성남시 분당구 정자동이다. 아래 거래 수는 당시 원본의 전체 기간 행 수이며 해제 거래를 포함한다. 이후 수집으로 숫자가 바뀔 수 있으므로 영구적인 기대값으로 하드코딩하지 않는다.

| 대장 root ID | 지번 | 실제 주거 또는 시설 | 당시 연결 거래 행 수 |
| --- | --- | --- | ---: |
| `hub:10891118021` | 121 | 상록우성, 301~328동 중 등록된 주거동 | 1,704 |
| `hub:10891118022` | 124 | 상록라이프1차, 101~110동 중 등록된 주거동 | 296 |
| `hub:10891118023` | 125 | 상록라이프2차, 201~205동 중 등록된 주거동 | 356 |
| `hub:10891118137` | 181 | 상록임광·보성, 401~408동 | 743 |
| `hub:10891118014` | 124 | 지하주차장만 주거동으로 잘못 분류된 별도 대장 항목 | 0 |

실제 등록 동 목록은 근거 JSON과 현재 공통 정보를 조회한다. 위 동 범위를 연속적인 전체 동 집합으로 추정해서는 안 된다.

라이프1차의 지도 ID는 `hub:10891118022`였고 `identity_ref`가 없었다. 저장 후 `refreshApartmentFavorites()`가 이를 `cohort:hub:10891118022:565c6b72ddd8a331e90d`로 갱신했다. `identitySelectionEqual()`은 범위 종류와 ID가 같아야 참이므로 지도 별표는 거짓이 되고, 해당 지도 항목의 즐겨찾기 전용 필터 결과도 0개였다. 저장 목록 자체에는 유효한 즐겨찾기가 있었다.

부속시설 두 건의 상세 원인은 다음과 같다.

| 건물 ID | 실제 용도 | 표제부 용도 코드 | 층별 용도 코드 | 주·부속 코드 | 세대·호수 |
| --- | --- | --- | --- | --- | --- |
| `10891120476` | 지하주차장 | `02000` 공동주택 | `02001` 아파트 | `0` | 모두 0 |
| `10891121410` | 경비실 | `02000` 공동주택 | `02001` 아파트 | `0` | 모두 0 |

`buildingClassification(title)`은 두 건을 `review`로 판단했지만 층별 자료를 넣으면 `apartment`가 됐다. `mainAtchGbCd === '1'`만 제외하는 조건으로는 이 사례를 잡지 못한다. 실제 용도가 부속시설뿐인 층별 자료를 아파트 용도 코드 하나로 승격시키는 경로를 고쳐야 한다.

이 ID들은 회귀 자료에만 사용한다. 운영 코드의 단지별 예외, 별칭 강제 추가, 지번 단독 병합 조건으로 사용하지 않는다.

## 3. 권장 데이터 계약의 구체화

아래 이름은 구현 예정 계약이다. 현재 DB나 API에 이미 있다고 가정하지 않는다.

### 3.1 식별자와 행의 단위

| 값 | 규칙 |
| --- | --- |
| `apartment_id` | 실제 대장 마스터를 가리킨다. 기존 `hub:` ID를 보존한다. |
| `selection_id` | 통합 조회 행의 선택 ID다. 기존 root·cohort·source ID를 사용한다. |
| `scope_kind` | `root`, `cohort`, `source` 중 하나다. |
| `identity_ref` | `{kind, id}`다. `scope_kind`와 `selection_id`가 같은 범위를 가리켜야 한다. |
| `root_ids` | 선택에 연결된 명시적인 root 집합이다. 여러 개이거나 미확정일 수 있다. |
| `active` | 현재 선택 자료로 사용 중인지 나타낸다. 비활성 상태가 원천 삭제를 뜻하지 않는다. |

통합 뷰는 선택 ID와 종류의 유일성을 보장하도록 구성하고, 생성 검증에서도 중복을 거부한다. 기존 root 전용 호출부는 `kind: 'root'`를 명시한다. source에 유일한 대장 root가 없으면 `apartment_id`를 임의로 채우지 않는다.

### 3.2 위치 계약

위치는 `location` 객체로 반환한다. 최소 필드는 `status`, `precision`, `latitude`, `longitude`, `building_id`, `entrance_index`, `source`, `observed_at`와 관련 출입구 참조다.

- `status`는 확인, 미확인, 여러 후보로 확정 불가를 구분한다. 미확인 좌표는 `null`이다. 0도 좌표나 빈 문자열을 대체값으로 쓰지 않는다.
- `precision`은 실제 출입구, 검증된 필지 수준, 미확인을 구분한다. 다른 정밀도의 좌표를 같은 수준의 근거로 사용하지 않는다.
- 대표 위치는 실제 관측된 위치 중에서 선택한다. 구역별 주거동 출입구를 우선하고, 선택 기준을 공통 모듈에 한 번 정의한다.
- 대표 위치 참조가 해당 단지 또는 구역에 실제로 속하는지 검증한다. 구역에 출입구가 없다고 부모 단지의 다른 구역 좌표를 복사하지 않는다.
- 지도용 대표점 선택과 단지 동일성 판정은 다른 정책이다. 대표점이 같아도 같은 단지로 합치지 않는다.

### 3.3 구역 계약

`area`는 선택 범위의 구역 요약과 원천 도형 참조를 반환한다.

| 필드 | 의미 |
| --- | --- |
| `identity_ref` | 이 구역 요약이 설명하는 선택 범위 |
| `geometry_scope` 또는 도형별 범위 참조 | 도형이 root 전체인지 특정 cohort인지 표시 |
| `legal_code`, `region_ids` | 법정동과 수집·행정구역 참조 |
| `parcels` | PNU, 지번, 주필지·부속 필지 관계, 확인 상태, 출처 |
| `boundary_refs` | 단지 필지 경계, 건물 외곽선의 ID·종류·범위·버전 |
| `bbox` | 검증된 도형의 표시 범위. 도형이 없으면 미확인 |
| `zoning_refs` | 용도지역의 ID, 이름, 출처와 자료 버전 |

경계의 공용 여부와 주소 구역의 배타적인 포함 여부를 구분한다. 공유 필지에 여러 단지 ID가 연결될 수 있다. root 수준 외곽선이 있다고 cohort 전용 외곽선으로 바꾸지 않는다.

실제 도형은 원천 관계와 ID로 보존한다. 공개 요약에 모든 GeoJSON을 반복 넣지 않는다. `geometry: 'full'` 같은 명시적 요청이나 지도 조각 생성 단계에서 공통 모듈을 통해 도형을 읽는다.

### 3.4 주거 상태와 화면 선택 상태

`residential_status`는 `residential`, `ancillary_only`, `unresolved`로 구분하는 것을 기본안으로 한다. `active`와 별개다. `map_visible`과 제외 사유는 공통 판정 결과에서 도출한다.

- 일반 아파트 선택의 기본 대상은 주거 용도가 확인된 항목이다.
- 부속시설만 확인된 항목은 일반 선택에서 제외하고 원천 증거를 보존한다.
- 주거 여부가 미확정인 항목은 검토 대상으로 남긴다. 원천 거래 내역까지 제거하지 않는다.
- 거래 미연결, 거래 자료 미수집, 조건에 맞는 거래 없음, 주거 판정 보류를 서로 다른 상태와 안내 문구로 다룬다.

### 3.5 API 계약과 재구성 내부 경로

다음은 목표 호출 형태다. 구현 시 현재 모든 호출부를 함께 이관한다.

```js
apartmentInformation(db, {
  kind: 'root',       // 'root' | 'cohort' | 'source' | 'all'
  activeOnly: true,
  geometry: 'summary', // 'summary' | 'full'
});

searchApartmentInformation(db, query, {kind: 'all'});
resolveApartmentIdentity(db, input, information);
publicApartmentInformation(db); // 공개 가능한 모든 범위의 공통 요약

// 신규 계획 API. 위 공통 정보의 지도 투영만 담당한다.
apartmentMapInformation(db, {scopeIds, generation});
```

`resolveApartmentIdentity()`는 기존의 `matched`, `ambiguous`, `unmatched`, `insufficient` 의미를 보존한다. 이름이나 좌표가 그럴듯하다는 이유로 `matched`를 반환하지 않는다. 공통 자료가 오래됐거나 생성이 실패한 경우는 자료 오류로 처리하고, 이를 정상적인 거래 0건이나 연결 해제로 바꾸지 않는다.

재구성 입력은 `apartment-identity.mjs` 내부의 원천 증거 읽기로 제한한다. 완성된 통합 뷰를 다시 그 뷰의 재구성 입력으로 삼지 않는다. `housingQueryInformation()`은 공통 공개 계약을 만드는 내부 구성 요소로 정리하고, 외부 호출부가 각자 공간 정보를 다시 보충하지 않게 한다.

## 5. 버전, 무효화와 공개 전환

공통 정보는 식별 자료와 공간 자료를 함께 다룬다. 거래 배정 파일의 해시만으로 공통 정보 캐시를 식별하면, 좌표·구역만 바뀐 경우를 구분하지 못한다.

공개 manifest에는 공통 카탈로그의 경로, 체크섬과 스키마 버전을 기록한다. 지도·검색·월별 조회 자료는 호환되는 공통 세대를 명시한다. 공통 카탈로그를 내용 해시가 있는 파일로 내보내고 최상위 manifest가 그 파일을 가리키는 방식을 우선한다. 현재 고정 `catalog.json` 경로의 모든 읽기와 검사도 함께 이관해야 한다.

상위 공개 카탈로그 버전과 개인 브라우저 설정 버전은 구분한다. 카탈로그를 확장한다고 개인 즐겨찾기 전체를 초기화하지 않는다.

비활성 부속시설의 기존 즐겨찾기를 설명하는 데 필요한 공통 상태도 조회 가능하게 보존한다. 일반 지도 선택에서 제외하는 것과 해당 식별자를 알 수 없는 값으로 만드는 것은 다른 작업이다. 공개 자료에는 검증을 통과한 최소 상태와 참조만 포함한다.

현재 게시 검사는 대장 단지 수와 지도 항목 수가 같다고 보는 부분이 있다. 주거 판정으로 지도 대상이 줄어들면 `등록 대장 수`, `선택 가능한 주거 단지 수`, `지도 위치 확인 수`를 각각 검증하도록 명시한다. 숫자를 맞추려고 미확정·부속시설 원천을 삭제하거나 검사 조건을 근거 없이 완화하지 않는다.

원천 변경이 있을 때의 의존 관계는 다음과 같이 검토한다.

| 변경 | 다시 확인할 내용 |
| --- | --- |
| 주거 분류·건물·주소·별칭·출입구 | 단지와 구역의 포함 관계, 위치, 거래·매물 연결과 공개 자료 |
| 필지 관계·검증된 경계 | 구역 포함 근거, 연결 검증, 지도와 공통 공간 자료 |
| 외곽선·용도지역 | 해당 공간 투영과 공개 자료 버전. 연결 판정에도 쓰는 자료면 그 판정까지 갱신 |
| 원본 거래 | 원천 이력, 유일한 거래 배정과 조회 자료 |

현재 `ensureSchema()`는 `apartment_identity`의 모든 UPDATE에 대해 주거 배정을 무효화한다. 파생 공간 결과를 배정 생성 뒤 같은 테이블에 쓰면 배정이 즉시 만료될 수 있다. 기본 정보와 필요한 공간 입력을 먼저 준비한 뒤 배정을 생성한다. 무효화 트리거를 조정한다면 원천 입력과 파생 출력의 의존 관계를 명시하고 재실행 검사를 추가한다.

공개 전환은 새 파일 생성 → 전체 정합성 검사 → 검증된 파일 배치 → 세대 포인터 manifest 갱신 순서로 한다. 중간 실패 때 마지막 정상 세대와 복구 자료를 보존한다. 파일 여러 개를 순차 복사하는 것을 전체 전환이 원자적이라고 간주하지 않는다. 서로 다른 세대를 읽은 경우에는 재조회 안내나 복구 경로를 제공한다.

## 6. 즐겨찾기 이관의 세부 조건

명시적인 root와 cohort를 같은 것으로 만드는 일반 비교 함수 변경은 금지한다. 다음을 분리해서 구현한다.

| 처리 | 기준 |
| --- | --- |
| 저장·삭제 | 저장된 정확한 `{kind, id}`를 대상으로 한다. |
| 지도 강조·즐겨찾기 필터 | 공통 정보가 선언한 표시 구역과 저장된 선택의 포함 관계를 사용한다. |
| 거래 조회 | 저장된 원래 범위와 검증된 거래 배정으로 조회한다. |
| 구형 값 갱신 | 동일성 또는 기존 의도의 보존을 증명하는 공통 근거가 있을 때만 변환한다. |

이미 cohort로 저장된 즐겨찾기를 root 지도 항목에서 표시할 때도 원래 cohort를 삭제·조회해야 한다. 동일 위치에 여러 범위의 즐겨찾기가 있으면 하나를 임의로 골라 지우지 말고 선택을 구분한다. 한 구역의 저장을 모든 형제 구역의 저장으로 확대하지 않는다.

`makeApartmentFavorite()`와 저장 갱신 함수에는 허용 필드 목록을 유지한다. 위치·구역·도형·원천 증거 객체를 통째로 복사하지 않는다. 현재 최신 카탈로그 행을 spread하는 갱신 코드가 이 점의 검토 대상이다.

| 즐겨찾기 | 실제 상록마을 4종 저장 후 공통 정보 갱신·해제·새로고침·즐겨찾기 필터, 구형 root와 기존 cohort 저장값 |

기존 회귀 테스트의 단지·구역 구분 기대값을 새 구현에 맞춰 약화하지 않는다. 실제 상록마을 데이터의 일부를 공개 가능한 최소 fixture로 옮겨 일반 fixture와 별도로 검사한다. 테스트는 작업 DB가 있어야만 실행되는 형태로 만들지 않는다.

새 테스트 파일의 이름과 위치는 구현 중 정하되, 분류·공통 정보·공개 투영 검사는 Node 테스트에, 화면 저장과 조회는 기존 Vitest 흐름에 둔다. 이전 설계 실험에서 만들었던 새 테스트 두 개는 현재 저장소에 없으므로 존재한다고 가정하지 않는다.

## 8. 승인 후 실행 명령과 주의할 순서

아래 명령은 **구현 승인 후** 코드와 호출 순서 변경을 마친 시점에 실행한다. 문서 작성만 요청받은 상태에서는 DB 갱신·추출·빌드를 실행하지 않는다.

먼저 작업 트리를 확인하고, 실행 중인 수집 작업이 있는지 읽기 전용으로 확인한다. 작업 DB를 SQLite 백업 API로 일관되게 백업한다. 복사본에서 마이그레이션과 전체 검증을 먼저 수행하고 결과를 검토한 뒤 작업 DB에 적용한다.

```powershell
git status --short
pnpm test
pnpm test:data
node --test tests/apartment-identity.test.mjs tests/housing-selection.test.mjs tests/housing-export.test.mjs tests/trade-link-resolution.test.mjs tests/apartment-master.test.mjs
pnpm audit:matches --output local/data-validation/apartment-matches-before.json
```

새 회귀 테스트를 위 검사에 포함한다. 현재 코드를 대상으로 정상 기준과 실패 기준을 구분해 기록한다. API나 수집 자료를 새로 받지 않아도 저장된 대장·층별·좌표·도형·거래 원천으로 우선 재구성한다.

코드 변경과 복사본 검증을 마친 뒤 공식 갱신 순서는 다음과 같다.

```powershell
pnpm data:apartments:rebuild
pnpm data:identities
pnpm data:export
pnpm data:verify
pnpm audit:matches --output local/data-validation/apartment-matches.json --before local/data-validation/apartment-matches-before.json
pnpm build
pnpm check:publish
```

현재 `data:apartments:rebuild`는 내부에서 대장 분류·거래 연결을 갱신하고 지도를 내보낸다. 따라서 위 순서를 실행하기 전에 **이 스크립트 내부의 공통 정보 준비 순서도 수정해야 한다**. 오래된 주거 배정을 가진 상태에서 기존 스크립트를 먼저 실행하는 것은 이 계획의 이관 절차가 아니다. 선택적 `--enrich-new`는 외부 API 보강을 수행하므로 기본 이관 명령에 포함하지 않는다.

또한 현재 대장 재구성 CLI에는 `--source` 인자가 없다. 검증용 DB 복사본을 대상으로 현재 명령을 그대로 실행하면 기본 작업 DB를 변경할 수 있다. 구현 단계에서 원천 경로를 지정할 수 있게 하거나, `rebuildApartmentMaster(db)`와 관련 공통 갱신 함수를 복사본 연결에 명시적으로 호출하는 검증 진입점을 준비한다. 반면 `data:identities`와 `data:export`는 현재 `--source`를 지원하고, 매핑 검사는 `--database`를 지원한다. 존재하지 않는 인자가 이미 구현돼 있다고 가정하지 않는다.

복사본의 추출 자료를 검사할 때는 기존 검사기의 경로 인자를 명시한다.

```powershell
node scripts/check-trade-data.mjs --target <복사본의-public/data> --source <작업-DB-복사본> --report local/data-validation/apartment-information-staged.json
```

이 명령은 별도 경로의 검사 예시다. 실제 경로를 정하고, 추출은 필수 검증이 내장된 `exportData` 또는 공식 추출 명령으로 수행한다. 직접 JSON을 편집하거나 검증 실패를 무시하지 않는다.

`pnpm dev`는 검색·지도 자료 준비 스크립트도 실행한다. 정상 데이터 생성과 검증 후 기존 로컬 서버를 재사용하거나 개발 서버를 띄운다. Codex 브라우저 패널에서 지도 → 즐겨찾기 → 단지 거래를 열어 확인한다. 패널 연결이나 실기기 검증이 불가능하면 그 한계를 완료 보고에 쓴다.

## 9. 중단과 복구 기준

- 원본 거래 ID·원문·건수가 달라지거나 한 ID가 여러 구역에 배정되면 공개 자료 전환을 중단한다.
- 지도 ID가 공통 정보에 없거나, 구역 근거가 좁은 범위로 오인되거나, 공간 버전이 섞이면 전환을 중단한다.
- 일부 실패를 정상적인 0건이나 자동 연결 해제로 바꿔 검사를 통과시키지 않는다.
- 생성 전 DB 백업, 마지막 정상 공개 세대, 실패 보고를 보존한다. 원천 테이블을 지우며 수습하지 않는다.
- 검증용 복사본 실패는 해당 복사본에서 수정한다. 작업 DB로 실패 상태를 옮기지 않는다.
- 이미 작업 DB를 갱신했다면 실행 중인 작업과 SQLite 파일 상태를 확인한 뒤 검증된 백업에서 복구한다. 원천 수집 중인 파일을 단순 덮어쓰지 않는다.

## 10. 구현 기록 — 2026-11-10

### 10.1 최종 구조와 조회 방법

물리적으로 모든 데이터를 큰 JSON 한 열에 복사하지 않았다. `apartment_identity`가 공통 식별·주거 판정과 대표 위치 참조를 보관하고, 출입구·필지·도형·용도지역은 기존 정규화 테이블에 유지한다. `apartment_information` 뷰와 `server/apartment-identity.mjs`의 공통 API를 조회 진입점으로 사용한다.

`apartment_identity`에 다음 열을 추가한다. 기존 DB는 `initializeApartmentIdentity`에서 누락된 열만 추가하므로 다시 실행할 수 있다.

| 열 | 역할 |
| --- | --- |
| `residential_status` | `residential`, `ancillary_only`, `unresolved` 판정 |
| `primary_building_id`, `primary_entrance_index` | 실제 관측한 대표 출입구의 복합 참조 |
| `spatial_generation` | 위치·구역·기본 속성 입력의 내용 해시 |
| `classification_evidence_json` | 연결 건물 ID와 분류 근거 |

`apartment_information`은 root·cohort·source를 `UNION ALL`한 뷰다. 같은 `apartment_id`에 여러 선택 행이 있을 수 있으므로 **`selection_id`와 `scope_kind`로 선택을 구분**한다. SQL에서 대표 이름·주소·선택 범위·위치를 확인하는 예시는 다음과 같다.

```sql
SELECT selection_id, scope_kind, apartment_id, canonical_name,
       residential_status, latitude, longitude, root_ids_json
FROM apartment_information
WHERE scope_kind = 'root' AND canonical_name LIKE '%상록마을%';
```

`location`, `area`, 관측 근거와 도형이 필요한 애플리케이션은 테이블을 직접 이어 붙이지 않고 아래 API를 사용한다. 직접 SQL 뷰는 source의 대표 좌표를 임의 추론하지 않는다. 공통 API는 검증된 유일한 구역이 있으면 그 구역 위치를 제공하며, 여러 구역이면 `ambiguous`로 반환한다.

```js
import {
  apartmentInformation, searchApartmentInformation,
  publicApartmentInformation, apartmentMapInformation,
} from './server/apartment-identity.mjs';

const selections = apartmentInformation(db, {kind: 'all'});
const matches = searchApartmentInformation(db, '상록마을', {kind: 'all'});
const details = apartmentInformation(db, {kind: 'cohort', geometry: 'full'});
const catalog = publicApartmentInformation(db);
const map = apartmentMapInformation(db, {
  scopeIds: ['dong_41135103'], generation: catalog.generation,
});
```

읽기 API는 스키마 변경이나 배정 갱신을 하지 않는다. 대장을 다시 구성하는 쓰기 경로가 기본 정보·공간 입력을 준비한 뒤 주거 배정을 재구성한다. 배정 생성 후 같은 식별 테이블을 수정해 배정이 다시 만료되는 순환을 만들지 않는다. 내부 재구성은 root 기본 정보만 읽으며 공개 자료를 다시 입력으로 사용하지 않는다.

### 10.2 위치·구역과 주거 판정

`server/apartment-spatial.mjs`가 원천 관계를 한 번 해석한다. 실제 주거동 출입구를 우선하고, 같은 우선순위는 건물 ID와 출입구 번호로 결정한다. cohort는 자신에게 등록된 건물의 출입구와 법정동·지번에 해당하는 필지만 사용한다. 출입구가 없으면 다른 구역 좌표를 빌리지 않는다.

경계 ID는 필지의 경우 `cadastral_parcels:<PNU>`, 건물의 경우 원래 footprint ID다. 공유 필지는 하나의 도형에 여러 root 소유 참조를 보존한다. cohort의 도형 참조도 실제 소유 범위가 root면 `geometry_scope`를 root로 유지한다. 같은 bbox 안에서 도형이 바뀌어도 참조 내용 해시와 공통 생성 버전이 달라진다.

`buildingClassification`은 층별 아파트 용도 코드가 붙어 있어도 실제 용도가 주차장·경비실·관리시설뿐인 행을 주거 근거에서 제외한다. 실제 주거 층이 함께 있거나 노인복지주택이 확인되면 주거 분류를 유지한다. 세대수 0이나 누락만으로 제외하지 않는다. 운영 코드에 상록마을 ID 예외는 없다.

지도 대상은 `active && residential_status === 'residential'`인 root다. 비활성·부속시설·미확정 항목은 공통 정보에서 삭제하지 않으며, 기존 선택을 열면 상태 안내를 제공한다. 대장 등록 수, 지도 선택 가능 수, 위치 확인 수를 별도 집계한다.

### 10.3 생성 파일과 버전 계약

새 공개 자료는 `version: 1`, `schema_version: 2`, `generation`, `apartments`를 갖는다. transport version은 유지하고 공간 계약 버전을 별도로 구분했다.

`server/apartment-information-files.mjs`가 UTF-8 파일의 바이트 크기·SHA와 파일명을 검증한다. `public/data/manifest.json`의 `apartment_information`이 활성 파일을 지정한다.

```json
{
  "file": "catalog-<sha256 앞 12자리>.json",
  "sha256": "<파일 전체 SHA-256>",
  "bytes": 24099643,
  "schema_version": 2,
  "housing_sha256": "<같은 내보내기의 주거 배정 파일 SHA-256>",
  "generation": "<공통 정보 내용의 SHA-256>"
}
```

`generation`은 `{schema_version: 2, apartments}`의 내용 해시다. 대장 가공 시각을 원천 관측 시각으로 사용하던 문제도 수정했다. 원천 수집 지역의 관측 시각이 있으면 그것을 사용하므로 같은 원천의 재구성은 같은 생성 버전을 만든다. 출처 관측이나 실제 위치·경계가 바뀌면 새 버전이 된다.

지도 manifest, 통합 검색과 조회 registry, 경계 조각은 같은 `apartment_information_generation`을 가진다. 월별 거래는 별도로 `housing.sha256`에 연결해 배정을 검사한다. 브라우저는 공통 카탈로그·지도·조각의 실제 해시를 검사하며, 새 metadata가 존재할 때 고정 `catalog.json`으로 우회하지 않는다. 호환 읽기는 새 metadata 자체가 없는 이전 자료에만 허용한다.

현재 카탈로그는 1,550개 선택, 약 24.1MB다. GeoJSON 전체는 포함하지 않지만 구역·위치 참조가 있어 기존 식별 목록보다 크다. 같은 페이지의 동시 요청은 공유하고, 최대 2개 항목·총 32M 문자 범위에서 현재 카탈로그를 캐시한다. 실제 크기의 자료로 동시·후속 로드가 파일 한 번 읽기로 끝나는 것을 확인했다. 추가 경량화가 필요하면 공간 참조를 별도 불변 사전으로 분리하는 방식을 평가하되, 조회 범위나 출처 정보를 제거해서 크기를 맞추지 않는다.

`exportData`는 임시 출력에 원본 거래·주거 배정·공통 카탈로그·지도를 만든 다음 검증한다. 공통 카탈로그의 조회 범위가 실제 주거 배정과 같은지도 확인하므로 SHA만 다시 계산한 잘못된 범위를 허용하지 않는다. 검증 후 파일을 배치하고 마지막에 주 데이터 manifest를 갱신한다. 파일 여러 개를 복사하는 작업 전체가 원자적인 것은 아니므로 브라우저의 생성 버전 검사를 유지한다. 대장 원천이 없는 작업 DB로 기존 대장 지도를 덮으려는 추출은 실패시키고 기존 파일을 보존한다.

### 10.4 즐겨찾기와 모바일 동작

- 새 지도 선택은 명시적인 root 참조다. 명시적인 root·cohort·source의 일반 동일성 비교는 바꾸지 않았다.
- 이전 무타입 root 즐겨찾기는 검증된 동일 도로명주소의 유일한 cohort로만 갱신한다. 지도는 공통 정보가 선언한 `map_member_refs`로 이 저장 상태를 표시한다.
- 지도에서 관련 저장 구역이 하나라면 그 **저장된 정확한 선택**을 해제한다. 여러 구역이 저장돼 있으면 `mixed` 상태와 구역 수를 표시하고 임의의 구역을 삭제하지 않는다.
- `makeApartmentFavorite`를 즐겨찾기 추가, 조회 선택, 관련 내역 이동, 공유 주소 복원에 적용한다. 저장 선택에는 위치·구역·GeoJSON을 넣지 않는다.
- 지도에서 거래 보기로 이동하면 전체 면적·취소 제외·최근 유효 거래 20건을 적용한다. 이전의 좁은 면적·기간 조건 때문에 저장한 단지가 없는 것처럼 보이는 문제를 막는다.
- 저장 대기·완료·실패 표시와 단지 거래 상단의 즐겨찾기 바로가기는 앞선 미커밋 수정과 함께 유지했다.

상록마을의 신규 root와 이전 즐겨찾기에서 갱신한 cohort가 다음 거래 수를 각각 유지했다. 취소 거래를 포함한 원인 분석 기록과 비교한 값이다. 실제 기본 화면은 취소를 제외한 최신 20건을 표시한다.

주차장 `hub:10891118014`와 경비실 `hub:10891118130`은 `ancillary_only`, 비활성 상태로 원천과 공통 정보에 남고 지도에서 제외된다. 같은 주소의 주거 root로 자동 합치지 않았다.

회귀 검사는 `tests/apartment-information.test.mjs`, `tests/apartment-spatial.test.mjs`, `tests/apartment-map-information.test.mjs`, `tests/building-classification.test.mjs`, `tests/rebuild-apartment-master-cli.test.mjs`, `tests/apartment-information-client.test.jsx`와 기존 식별·주거 배정·지도·데이터 무결성 검사에 있다. `tests/sangnok-identity.test.mjs`는 이 문서의 공개 진단 근거에서 실제 네 단지의 ID·주소·거래명과 부속시설 두 건의 용도를 읽어 검사하므로 작업 DB 없이 실행할 수 있다. 새 필드 누락, 보조시설의 층별 오분류는 수정 전 실패를 확인했다. 이후 같은 bbox의 도형 변경, 재실행 버전 안정성, 잘못된 해시·세대·경로, 해시를 다시 계산한 조회 범위 위조, 구역 즐겨찾기 해제를 검사했다.

실제 생성 파일을 사용한 Chromium 모바일 검사에서 Pixel 5 조건 393px와 iPhone 13 사용자 에이전트 조건 320px를 확인했다. 저장 → 새로고침 → 즐겨찾기만 보기 → 최근 20건 조회 → 공유 주소 복원 → 기존 cohort 갱신 → 정확한 해제가 통과했다. 가로 페이지 넘침과 처리되지 않은 페이지 오류는 없었다. **실제 Android 기기나 iPhone Safari 엔진 검증을 수행한 것은 아니다.**

검사 로그와 JSON 근거는 `local/apartment-implementation/`에 있다. `raw-preservation.json`, `copied-export-validation.json`, `copied-browser-validation.json`, `rebuild-generation-validation.json`, `sangnok-validation.json`, `mobile-validation.json`을 구분해 보관한다. 기존 미확정 거래·매물은 추가 연결 근거 없이 확정하지 않았으며, 목록은 `local/data-validation/apartment-matches.json`에서 확인한다.

### 10.6 다음 변경 시 실행 순서

수집 작업이 없는지 확인한 뒤, 복사본에서 `data:apartments:rebuild --source <DB> --target <복사본 지도 폴더>`와 공식 추출을 먼저 검증한다. 복사본의 브라우저 자료 준비는 다음처럼 실행할 수 있다.

```powershell
node scripts/prepare-browser-data.mjs --public-root local/apartment-implementation/staged-public
node scripts/check-trade-data.mjs --source local/apartment-implementation/working.sqlite3 --target local/apartment-implementation/staged-public/data --require-search --report local/apartment-implementation/copied-browser-validation.json
```

기본 작업 DB에 반영할 때는 다음 순서를 사용한다. `--enrich-new`는 외부 API 보강이 필요할 때만 별도로 선택한다.

```powershell
pnpm test:node
pnpm test
pnpm test:data
pnpm data:apartments:rebuild
pnpm data:identities
pnpm data:export
pnpm data:verify
pnpm audit:matches --output local/data-validation/apartment-matches.json
pnpm build
pnpm check:publish
```

`data:identities`는 카탈로그를 생성하지만 주 manifest의 공개 세대 전환을 단독으로 완료하지 않는다. 이어서 `data:export`와 빌드를 실행해야 한다. 실패한 검사를 생략하거나 이전 파일과 새 metadata를 수동 조합하지 않는다. 로컬 서버가 실행 중이면 최신 manifest 응답과 실제 화면을 확인해 재사용하고, 아니면 `pnpm dev`를 실행한다. 커밋·푸시·배포는 별도의 현재 작업 지시가 있을 때만 수행한다.
