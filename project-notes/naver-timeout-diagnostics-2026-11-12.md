# 네이버 수집 시간 초과의 단계별 기록

2026-11-12 로컬·GitHub 비교 진단 기록이다. 세 차례의 원격 실행에서 GitHub 공용 실행 환경은 `fin.land.naver.com`의 첫 HTTP 응답을 받지 못했다. 마지막 비교에서는 일반 인터넷·네이버 홈·기존 부동산 홈은 정상 응답하고, `new.land`·`m.land`·`fin.land`에서만 같은 현상이 발생했다. 접속 환경에 따른 부동산 서비스의 HTTP 응답 문제까지 확인했으며, 정확한 서버 정책이나 중간 네트워크 장비는 미확정이다. 로컬 성공을 원격 수집 성공으로 보고하지 않는다.

## 기존 기록의 문제와 수정

기존 Python 작업은 브라우저 이동·렌더링·매물 응답을 같은 `timeout`으로 반환했다. 내부 완료 기한도 페이지 이동이 끝난 뒤 새로 계산해, 이동 전부터 시작한 상위 제한 시간이 먼저 종료될 수 있었다. 기존 로그만으로 문서 접속 실패와 매물 API 대기를 구분하기 어려웠다.

현재는 요청 예산을 하나로 계산한다. 기본 Node 제한 90초 중 Python 작업은 80초를 사용하고 나머지는 실패 기록과 종료에 사용한다. fin 단지 이동 응답은 최대 20초, 개별 브라우저 상태 조회는 최대 5초로 나눈다. 실패 상태·스크린샷은 각각 최대 2초만 기다린다.

## 보존하는 자료

- `local/data-validation/naver-live.json`: DNS/TLS, 전체 결과, 실패 단계, 추적 파일 경로
- `local/data-validation/naver-browser/<UUID>.jsonl`: 브라우저 시작부터 UTC 시각·경과 시간·단계·요청/응답 건수
- 같은 UUID의 `.png`: 실패 당시 익명 공개 화면; 캡처가 실패하면 그 사실도 기록

JSONL은 작업 중 바로 기록하므로 부모 프로세스가 작업을 종료해도 완료한 단계가 남는다. 반복 기록은 제한하고 마지막 실패·완료 기록은 보존한다. Git 제외 경로에만 저장한다. 쿠키·인증 헤더·응답 원문·페이지 본문·URL 쿼리는 추적 파일에 넣지 않는다. 페이지 상태에는 경로, readyState, 본문 글자 수, 매물 링크 수, 접근 제한 문구의 유무만 기록한다.

Node의 DNS/TLS 검사는 Chrome과 별개의 연결 경로다. DNS·TLS 성공만으로 Chrome의 페이지 로딩이나 네이버의 접근 허용을 확정하지 않는다. 프록시 값은 기록하지 않고 설정 여부만 남긴다.

| 이벤트·단계 | 확인하는 사실 |
| --- | --- |
| `browser_start` → `browser_ready` | Chrome 실행·새 탭·관측 준비 |
| `navigation_ack` | 페이지 이동 명령의 반환 여부 |
| `document_request`, `document_redirect`, `document_response` | 문서 요청·리디렉션·HTTP 상태·연결 시간 |
| `dom_content_loaded`, `document_render` | 렌더링과 브라우저 제어 응답 |
| `list_request`, `list_response_headers`, `list_response_body` | 매물 요청·응답·파싱·다음 페이지 유무 |
| `first_list_request`, `first_list_response`, `next_list_response` | 완료되지 않은 대기 조건 |
| `network_failed` | Chrome의 `net::ERR_*`와 취소 여부 |
| `operation_failed`, `failure_state` | 실패 단계·마지막 완료 단계·페이지 상태 |

HTTP 200이어도 전체 매물 응답과 주소 검증을 통과해야 성공이다. 시간 초과·접근 제한·매물 0건은 구분한다.

## 검사와 남은 확인

실제 Chrome을 사용하는 재현 서버에서 문서 응답을 멈추면 `navigation_ack`, 매물 응답만 멈추면 `first_list_response` 대기로 구분됐다. 두 경우 모두 완료 단계·요청/응답 건수가 파일에 남았다. 부모 오류에도 단계와 파일 경로가 보존된다. 기존 검색·공유 범위·전체 페이지 수집을 포함한 단위·Chrome 통합 검사 27개, 데이터 검사 46개가 통과했다.

현재 확인한 것은 로컬 네트워크·렌더링·매물 응답이 정상이라는 사실이다. GitHub에서 HTTP 응답 전 정지인지, HTML 이후 렌더링 정지인지, 매물 요청 이후 정지인지는 새 원격 추적 파일로 판별해야 한다. IP 차단·네이버 정책·DNS 장애 중 어느 하나로 아직 확정하지 않는다.

최종 명령은 로컬 동결 기준본의 활성 승인과 위치 문맥을 확인한 뒤 다시 실행했다. `naver-diagnostics-approved.json`에서 기준본 세대가 일치했고 같은 단지 34건·1페이지가 8,519ms에 완료됐다. DNS 19ms·TLS 53ms였으며 추적 파일은 `e9b0d8e0-2bee-48f1-bc03-281a1d162bf2.jsonl`이다. 두 번의 실제 성공을 확인했다. 원천 DB와 공개 매물은 변경하지 않았다.

필수 `data:verify`, 원본 대조를 포함한 `build`, `check:publish`, 연결 감사와 `git diff --check`도 통과했다. 이 기록 시점의 변경은 커밋하지 않았다. 프로젝트의 작업별 명시적 커밋·푸시 규칙에 따라, 원격 코드 반영과 새 GitHub 진단 실행은 승인을 기다린다.

Node의 TLS·HTTP/1.1·HTTP/2 검사는 각 호스트에서 DNS로 선택한 동일 IP를 사용했다. Ubuntu는 `202.179.180.81`, Windows는 `110.93.151.131`이었다. 두 호스트 모두 프록시 환경변수는 설정되지 않았다. Chrome이 선택한 원격 IP는 문서 응답이 없어 이 자료에서 확인할 수 없다.

확인한 실패 범위는 **GitHub 공용 실행 환경에서 네이버의 첫 HTTP 응답 헤더를 받는 단계**다. 브라우저를 사용하지 않는 두 HTTP 방식에서도 재현됐으므로 Chrome 제어만의 문제로 설명할 수 없다. 아파트 ID 매핑·DOM 선택자·스크롤·매물 파싱은 아직 실행되기 전이다. 정상인 로컬에서는 같은 공개 주소가 HTTP 307로 `/map`에 연결되고 전체 매물 검증까지 완료됐다.

정확한 네트워크 장비·서버 정책은 외부에서 확정하지 못했다. IP 차단·지역 제한·봇 정책을 뜻하는 HTTP 403/429나 안내 문구를 받은 것은 아니다. 따라서 “IP 차단이 확정됐다”거나 “HTTP 200인데 파싱에 실패했다”고 기록하지 않는다.

운영 해결책은 성공이 확인된 네트워크에서 수집을 실행하거나 네이버가 허용하는 접속 경로를 확보하는 것이다. GitHub 실행을 유지하려면 해당 네트워크의 self-hosted runner를 검토할 수 있다. 이번 작업에서는 runner 설치·네트워크 우회·연결 변경을 수행하지 않았다. 기존 승인 ID와 마지막 성공 자료는 보존했다.

두 번째 실행에서도 두 운영체제의 수집기 단위·실제 Chrome 재현 테스트는 통과했다. 실패는 실제 외부 네이버 접속 단계로 한정됐다. 진단 코드는 시간 초과를 빈 매물이나 수집 성공으로 바꾸지 않고 추적 자료를 보존했다.

두 원격 환경의 모든 경로에서 DNS와 검증된 TLS 1.3 연결은 성공했다. `*.land.naver.com` 인증서의 발급자와 SHA-256 지문은 로컬과 원격이 같았다. 네이버 홈은 로컬과 원격에서 서로 다른 정상 인증서를 받았으며, 모두 검증과 HTTP 200 응답에 성공했다. 인증서 차이를 장애로 해석하지 않는다.

원격 Windows와 로컬은 `fin.land.naver.com` 검사에서 같은 목적지 IP `202.179.180.91`에 연결했다. 원격은 네 경로 모두 시간 초과됐고 로컬은 모두 응답했다. 따라서 DNS가 서로 다른 서버를 선택했다는 설명만으로 이번 차이를 설명할 수 없다. 동일 IP가 항상 동일 내부 서버를 뜻하는 것은 아니므로 특정 장비까지 확정하지 않는다.

이 실행에서도 두 운영체제의 수집기 테스트 단계는 통과했다. 실제 외부 수집은 Chrome 준비 후 문서 요청 1건·응답 0건에서 멈췄고, 20초 뒤 `navigation_ack` 시간 초과를 기록했다. 매물 API 요청은 0건이다. 별도의 HTTP/1.1·HTTP/2 검사도 첫 응답을 받지 못했다.

같은 시각 로컬에서는 같은 기준본 세대와 승인 단지 `107215`로 실제 Chrome 수집을 다시 실행했다. 광고 36건·1페이지를 7,778ms에 수집하고 위치·주소 검증을 통과했다. 앞선 34건과 관측 시각이 다르므로 광고 수 차이를 자료 누락으로 해석하지 않는다. 결과는 `local/data-validation/naver-diagnostics-comparison.json`, 추적은 `f125b73e-b5aa-4145-98c8-3480c0813d64.jsonl`이다. 진단 명령은 작업 DB와 공개 매물 스냅샷을 갱신하지 않았다.

## 원인 판단과 운영 해결 방향

확인된 직접 원인은 **GitHub 공용 실행 환경에서 부동산 서비스의 첫 HTTP 응답을 받지 못해 수집을 시작할 수 없는 현상**이다. 일반 인터넷 전체 장애나 특정 단지 주소의 오류로는 관측 결과를 설명할 수 없다. 홈페이지와 `robots.txt`에서도 재현되므로 매물 API 인증, 승인 ID 매핑, DOM 선택자, 목록 파싱보다 앞선 문제다. Chrome과 독립된 HTTP 검사도 실패하므로 브라우저 제어 방식만 바꾸는 것으로 해결된다는 근거가 없다.

접속 환경에 따른 네이버 부동산의 서버·보호 계층 정책 또는 해당 경로의 네트워크 처리를 원인 후보로 남긴다. 어느 쪽이 응답을 멈췄는지 확정하려면 제공자 측 요청·보안 로그나 중간 장비의 관측이 필요하다. 이번 검사에서 403·429 응답, 차단 안내, 정책 이름은 관측하지 못했다. 따라서 해외 IP 차단이나 데이터센터 IP 차단으로 단정하지 않는다. 6초의 HTTP 검사와 20초의 Chrome 관측을 넘어 응답이 영구히 오지 않는다고 주장하지도 않는다.

운영 변경의 우선안은 성공이 확인된 네트워크에서 수집 작업을 실행하고, GitHub가 로컬 확정 기준본과 ID를 전달해 수집 이력·원천 매물을 이어받게 하는 것이다. 로컬 전체 DB로 클라우드의 최신 수집 DB를 덮어쓰는 방식은 사용하지 않는다. GitHub 공용 runner를 유지하려면 제공자에게 해당 실행 환경의 접속 허용 여부와 정상 수집 경로를 먼저 확인해야 한다. 시간 제한 연장은 진단 지표를 바꿀 뿐, 현재 확인한 접속 문제를 해결한다는 근거가 없다.

이번 작업에서는 수집 실행 위치, runner 설치, 접속 경로, 승인 ID 연결을 변경하지 않았다. 원격 실제 수집은 여전히 실패 상태다. 서비스별 비교 진단은 `node scripts/diagnose-naver-endpoints.mjs`로 재실행할 수 있으며, 기존 워크플로가 원격 결과를 아티팩트로 보존한다.
