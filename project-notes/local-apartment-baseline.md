# 로컬 확정 아파트 기준본의 전달과 수집 이력 보존

작성일: 2026-11-11. 이 문서는 [데이터 소유권 운영 규칙](data-ownership-and-provider-identities.md)을 실행 코드에 적용한 범위와 재검증 방법을 기록한다.

## 해결하는 문제

과거에는 GitHub에서 복원한 전체 DB의 대장·주소·네이버 연결을 다시 계산했다. 로컬에서 수정한 연결과 다른 오래된 대장이 수집 대상과 공개 지도에 사용될 수 있었다. 반대로 이를 해결하려고 로컬 전체 DB를 올리면 클라우드의 최신 거래·매물 관측을 잃을 수 있다.

이제 두 자료를 별도로 전달한다.

| 전달 자료 | 확정 주체 | 다음 실행에서의 처리 |
| --- | --- | --- |
| `automation/apartment-baseline/manifest.json`과 지정 gzip | 현재 로컬 작업 DB | 무결성·지역 범위를 확인하고 아파트 기준으로 설치 |
| 암호화된 클라우드 수집 DB | GitHub의 이전 수집 실행 | 거래·매물·원문·행 ID·수집 이력을 보존 |

기준본 설치는 수집 이력 DB 전체를 교체하지 않는다. 로컬 PC의 원본 DB에는 동결 기준본을 설치하지 않는다. 로컬 원본에서 검토·수정하고 새 기준본을 생성하는 운영을 유지한다.

## 선택한 구조

대장 원문을 포함한 1.7 GB 전체 DB를 매번 전달하는 대신, 로컬에서 확정한 조회 정보·연결 규칙·지도를 콘텐츠 해시가 있는 압축 패키지로 만든다. 클라우드는 이 준비된 정보를 읽고 최신 시장 자료의 배정과 통계만 갱신한다. 옛 DB의 이름·주소·좌표로 단지 연결을 다시 추론하지 않는다.

기준본의 JSON 구성은 다음과 같다.

| 필드 | 내용 |
| --- | --- |
| `information` | 단지·주소 구획·원천 선택의 이름, 별칭, 위치, 구역, 조회 범위 |
| `housing` | 로컬 확정 root·cohort·source 관계, 등록 건물 범위; 거래 건수는 실행 시 재계산 |
| `targets` | 일일 네이버 수집 대상과 위치 검증 문맥, 공유 단지의 명시적 범위 |
| `providers.molit` | 공식 `aptSeq` → 로컬에서 확인한 기존 원천 참조 목록 |
| `rules` | 기존 원천별 등록 동·준공연도 배정, 충돌하는 관측의 정확한 예외 |
| `tables` | 지역·도로명주소·네이버 승인·원천 연결의 작은 SQL 자료 |
| `map` | 로컬에서 만든 단지 지도와 경계 |
| `memberships`, `links` | 내보내기 검증에 필요한 확정 소속과 기존 참조 |

거래, 네이버 광고, 수집 실행, API 응답 원문은 이 패키지에 넣지 않는다. 공급자 연결 규칙의 정확한 재현에 필요한 예외에는 원문의 해시만 사용한다. 네이버의 검증 근거는 승인 연결과 함께 유지한다.

### 버전과 무결성

`generation`은 압축 전 JSON 전체의 SHA-256이다. `scope_sha256`은 정렬한 수집 지역 ID 목록의 해시다. `connections_sha256`은 실거래 공급자 연결·배정 규칙·네이버 대상·승인 연결·원천 연결을 함께 묶은 해시다.

manifest는 압축 파일명·바이트 수·SHA-256, 압축 전 크기·SHA-256도 가진다. 파일명은 `baseline-<generation 앞 12자리>.json.gz`다. 파일 경로와 95 MB 제한도 검증한다. 생성 시 패키지를 먼저 쓰고 manifest를 마지막에 교체한다.

기준본 파일 누락, 손상, 지원하지 않는 버전, 다른 지역 범위, 체크아웃과 설치 DB의 세대 불일치는 실행 실패다. 옛 DB의 연결로 우회하지 않는다.

### 설치 트랜잭션과 쓰기 차단

`installApartmentBaseline`은 한 트랜잭션에서 다음 네 테이블과 `local_apartment_baseline`을 갱신한다.

- `regions`
- `road_addresses`
- `apartment_naver_matches`
- `apartment_naver_sources`

위 다섯 테이블에는 INSERT·UPDATE·DELETE 차단 트리거를 설치한다. 새 기준본 설치만 자체 트랜잭션 안에서 이 트리거를 교체한다. 중간 제약 조건 오류가 발생하면 기존 내용과 차단 트리거가 함께 복구된다. 수집·내보내기·보관 전에 테이블 내용도 패키지와 다시 비교한다.

`trades`, `molit_*`, `collection_runs`, `api_pages`, `naver_listing_snapshots`, `naver_listing_days`는 설치 대상이 아니다. 거래 배정·카운터용 `housing_identity_*`는 확정 규칙과 현재 거래에서 다시 만드는 파생 자료다.

복원 DB의 큰 대장 원문 테이블이 남아 있어도 클라우드 수집·공통 정보·지도 생성 경로는 이를 사용하지 않는다. `synchronizeApartmentIdentity`와 네이버 연결 승인 함수도 설치 DB에서 실행을 거부한다. 실제 검증 복사본의 옛 대장 이름과 수집 완료 상태를 의도적으로 바꿔 이 조건을 검사한다.

## 새 실거래의 배정

1. 원문의 공식 `aptSeq`가 있으면 기준본의 승인 목록에서만 source를 선택한다.
2. 원문의 source가 그 목록에 있거나, 승인 source가 하나로 확정된 경우에만 사용한다. 여러 후보가 남으면 미확정으로 보존한다.
3. 확정 source의 등록 동 표기·준공연도 조합 또는 명시적인 원문 해시 예외로 배정한다.
4. 관측하지 않은 조합의 기본 배정은 `unresolved`다. 단지 연결이 승인됐다는 이유로 새 동을 자동으로 root/cohort에 포함하지 않는다.
5. 공식 ID가 아직 없는 기존 자료는 로컬에서 동결한 기존 source 규칙을 호환 경로로 사용한다. 이것을 공식 공급자 ID라고 부르지 않는다.

공식 ID가 새롭거나 미승인이면 이름·지번이 일치해도 승인된 건물 연결로 승격하지 않는다. 원본 거래와 원천 단지 전체 조회는 보존하고, 새 원천에는 위치·구역 미확정 상태를 표시한다. 기준본 밖의 단지를 원문에서 삭제하지 않는다.

공식 ID는 같고 원문의 이름·지번 표시가 바뀌면 단일 승인 연결을 사용한다. 이 경우 공개 주거 배정에 `provider_apartment_id` 증명을 넣고, 브라우저의 원문 `raw.aptSeq` 및 승인 목록과 대조한다. 검색도 원문의 표시 이름 대신 검증된 배정 source를 사용한다. 개별 거래 행 ID는 별도로 유지한다.

배정 규칙을 생성할 때 현재 로컬의 모든 거래를 다시 계산해 기존 배정과 정확히 같은지 확인한다. 충돌하는 동·준공연도 조합은 임의로 하나를 고르지 않고 정확한 관측 해시 예외로 남긴다. 이후 다른 원문으로 바뀐 미확정 자료는 로컬에서 다시 검토해야 한다.

## 네이버 수집과 공개 자료

일일 수집은 기준본 `targets`와 현재 범위 해시가 유효한 `verified` 승인만 사용한다. 공유 네이버 번호도 기존의 명시적인 대표 범위·동 검증 문맥을 전달한다. 수집 중 후보 검색, 연결 승인, 주소 수집은 실행하지 않는다. 클라우드에서는 JUSO 키가 없어도 수집할 수 있다.

같은 날 재실행은 동일 기준본 세대의 시도만 이어받는다. 로컬 기준본이 바뀌면 같은 날이어도 새 대상 기준으로 확인한다. 일시 수집 실패가 확정 연결을 지우지 않는다.

클라우드 DB와 체크아웃의 초기 매물 스냅샷이 함께 있으면 설치 모드에서는 DB 관측을 우선한다. 초기 스냅샷의 늦은 실패 시각 때문에 더 오래된 광고가 최신 관측을 가리는 문제를 방지한다. DB에 관측이 없는 대상만 초기 스냅샷으로 보충한다. 현재 승인 ID·번호·범위와 다른 공개 그룹은 제외하되 DB 원문은 보존한다.

공개 자료의 다음 위치에 기준본 연결을 기록하고 서로 대조한다.

- `data/manifest.json.apartment_baseline`: 세대·범위·연결 해시
- 공통 아파트 정보와 주거 배정 파일: `baseline_sha256`
- `query-data/manifest.json.apartment_baseline`
- `apartment-map/manifest.json.apartment_baseline`

검색·지도·월별 조회는 공통 아파트 정보의 생성 버전과 주거 파일 해시도 기존과 같이 검사한다. 서로 다른 기준본의 파일을 섞으면 검증을 실패시킨다.

## 로컬 운영 절차

아파트 기본 정보·위치·구역·공급자 연결을 현재 로컬 원본 DB에서 확정한 다음 실행한다. 기준본의 원천으로 예전 백업 DB나 클라우드 복원 DB를 사용하지 않는다.

```powershell
pnpm data:identities
pnpm data:export
pnpm data:baseline:create
pnpm data:baseline:check
```

생성된 기준본을 직접 편집하지 않는다. 승인 변경은 로컬 원본을 수정한 뒤 재생성한다. 생성기에는 `--source`, `--public-root`, `--directory`를 지정할 수 있으나 원본 DB와 지도는 같은 로컬 확정 세대여야 한다.

새 복사본 검증은 다음과 같다. 대상 파일이 이미 있으면 검증기가 실패하므로 새 경로를 지정한다.

```powershell
node scripts/verify-apartment-baseline.mjs --database local/apartment-baseline-validation/working.sqlite3
```

검증기는 현재 로컬 DB를 SQLite backup으로 복사하고 원천 테이블의 순서 있는 전체 해시를 기록한다. 기준본 설치 후 모든 거래 배정이 같은지, 원천·수집 이력이 그대로인지, 옛 대장을 바꿔도 수집 대상과 공통 정보가 같은지 확인한다. 결과는 `local/apartment-baseline-validation/report.json`에 쓴다. 로컬 원본은 읽기 전용으로 연다.

설치된 수집 DB를 별도로 검사할 때는 다음 명령을 사용한다.

```powershell
pnpm data:baseline:apply --database local/apartment-baseline-validation/working.sqlite3
```

이 명령을 편집 가능한 로컬 원본에 실행하지 않는다. 자동화는 복원 임시 DB에 기준본을 설치하고 검증한 뒤에만 작업 DB로 교체한다. 이후 repair·collect·export·save가 각각 체크아웃의 기준본과 설치 DB를 대조한다.

커밋·푸시·배포는 별도 사용자 명령이 필요하다. 기준본 생성이나 검증은 그 권한을 포함하지 않는다.

## 남은 작업

전체 과거 월의 공식 실거래 단지 ID 보강은 별도 작업이다. 현재 878건에서 확인한 169개 공식 단지 연결만 패키지의 `providers.molit`에 들어간다. 나머지 과거 거래의 호환 source 참조를 공식 ID로 간주하지 않는다. 새 ID와 새 건물 표기가 유입되면 원문을 보존하고 로컬 검토 후 새 기준본으로 승인한다.

이 작업은 GitHub에 배포되지 않은 로컬 변경이다.

## 실제 DB 검증 기록

현재 로컬 원본 `local/my_real_estate.sqlite3`를 새로 복사해 적용했다. 검증 DB는 `local/apartment-baseline-validation/working.sqlite3`다. 과거 복원 DB를 아파트 기준으로 사용하지 않았다.

| 항목 | 확인 결과 |
| --- | --- |
| 기준 세대 | `2231257a459bd8c29b85b48f1faba05d0f4cf4fdbcd3989dac9e4ab49d511a2d` |
| 연결 해시 | `60c2878955116d3581fe87b5d6bcd08322a2f6a7155965ba2bcf1aa0b9cea483` |
| 패키지 크기 | 압축 8,923,923 bytes / 원본 56,180,323 bytes |
| 거래 재현 | 344,537건의 기존 배정 해시 일치 |
| source / cohort | 612 / 470 |
| 네이버 대상 | 469곳, 현재 범위가 유효한 승인 389곳 |
| 실거래 공식 연결 | 관측된 공식 단지 ID 169개 |
| 원천 보존 | 거래·API 페이지·실행·MOLIT 원장/원문/소속·매물 스냅샷/일일 보고 해시 모두 일치 |
| 옛 대장 무시 | 복사본의 모든 대장 이름과 지역 수집 상태를 바꿔도 공통 정보·대상 유지 |
| 실제 상세 API 재수집 | 분당구 202611 25건, 공식 ID 25건, 기존 행 ID 25개 유지, 신규·퇴역 0개 |
| 실제 네이버 재수집 | 2623번 131개 매매 광고, 전체 페이지 확인 |
| 공유 단지 조회 | 라이프1차 63개 / 라이프2차 68개, 광고 ID 교집합 0개 |

실제 수집은 검증 복사본과 `local` 결과 파일에서 수행했다. 네이버 raw 131개는 두 대상의 제공자 관측으로 보존하고, 화면 조회에서 로컬 확정 동 범위로 제한했다. 개별 광고·중개사 가격을 합치지 않았다. 이 결과는 전체 389개 승인 단지의 신규 수집 성공을 의미하지 않는다.

재검증 자료는 `report.json`, `molit-collection.json`, `naver-2623-report.json`, `naver-scopes.json`, `export.json`, `final-export.json`이다. 모두 `local/apartment-baseline-validation/` 아래의 Git 제외 자료다. 원본 DB는 동결하지 않았다.
