# 사용자 경험 개선 실행 계획 — 2026-10-18

분석 근거: [종합 진단](USER_EXPERIENCE_AUDIT_2026-10-18.md), [측정 JSON](USER_EXPERIENCE_MEASUREMENTS_2026-10-18.json).

이 문서는 제안 계획이다. 이번 작업에서는 기능을 수정하거나 커밋·푸시하지 않는다. 범위별로 구현·검증하여 이미 좋은 월별 데이터 분할과 지역/단지 공통 거래 화면을 유지한다.

## 1단계 — 검색이 실제 거래 자료를 빠짐없이 찾도록 수정 (P1)

### 문제와 변경

첫 화면은 지도 마스터 467개만 검색한다. 실거래 카탈로그에 존재하는 벽적골우성·주공그린빌3·꽃메마을힐스테이트가 검색되지 않는다.

1. 빌드 시 3개 시군구의 거래 카탈로그로 경량 통합 검색 인덱스를 만든다. 사용자가 검색을 시작할 때 한 번만 불러온다.
2. 실거래의 지역·법정동·지번·이름을 기본 키로, 지도 `master_id`와 별칭을 보강 정보로 연결한다. 지도 좌표가 없어도 검색과 조회는 가능하게 한다.
3. 이전 명칭과 여러 필지는 검증된 연결만 묶고, 동명이인·다른 지번은 주소로 구분한다. 원천 키 612개를 무조건 612개의 실제 단지로 표시하지 않는다.
4. 최근 거래일·자료 제공 여부·위치 미확인 상태를 필요할 때만 간단히 보여 준다.
5. 메모리 캐시와 실패 후 재시도를 공유한다. 새 버전 인덱스로 바뀌면 이전 캐시는 갱신한다.

### 완료 기준

- 재현 검색어 3개와 기존 정상 단지가 모두 해당 거래로 연결됨.
- 별칭으로 찾은 결과와 지도에서 선택한 결과가 같은 거래 키 집합을 조회함.
- 지도 미연결/좌표 없음이 거래 검색 누락으로 이어지지 않음.
- 기간 거래 없음과 단지 없음이 구분됨.
- 최초 검색에 전체 거래 원본·지도 경계를 받지 않음. 최초 검색 인덱스의 압축 용량은 현재 약 50KB와 비교하고 증가 이유를 기록함.

## 2단계 — 아파트 지도 초기 로딩과 확대 비용 축소 (P1)

### 문제와 변경

현재 경계 원본 약 10.4MB를 전부 수신·검증해야 지도가 열리고, 확대 시 SVG 경로 약 9,400개가 만들어진다.

1. 단지 목록/중심점은 경계와 독립적으로 표시한다. 지도 타일·경계 실패에도 검색·목록·거래 조회가 가능하게 한다.
2. 경계를 우선 시군구/동 단위 해시 파일로 분할한다. 단지 수가 늘 때를 고려해 공간 타일 방식도 비교한다.
3. 지도의 현재 bbox와 확대 수준에 필요한 파일·도형만 받는다. 낮은 확대는 단순화 경계 또는 묶음 마커를 사용한다.
4. 상세 건물 외곽선은 확대 또는 선택한 단지에 한정한다. 범위 밖 레이어는 정리한다.
5. 파일별 형식 검증은 유지하되 같은 해시의 검증·파싱 결과를 제한된 캐시에서 재사용한다.
6. 공간 범위 제한 후 Canvas/SVG의 선택·툴팁·키보드·별표 동작을 비교해 렌더러를 결정한다.
7. 경계 로딩 진행과 실패를 점/목록 사용을 막지 않는 상태로 표시한다.

### 완료 기준

- 지도 탭을 열지 않은 첫 방문에 경계 파일 요청 없음.
- 지도 첫 화면·모바일 목록 모드에서 전체 상세 경계 일괄 수신 없음.
- 경계 레이어를 끄면 미수신 경계는 받지 않음.
- 확대·이동 때 생성되는 도형 수가 현재 화면의 데이터 규모에 비례함. 전체 8,928 feature를 무조건 생성하지 않음.
- 지도 선택 위치, 팝업, 층수, 즐겨찾기, 거래 화면 이동, 필터 초기화, 타일 출처 표기 회귀 확인.
- 같은 감속 조건에서 기존 22.1초와 재측정. **프로젝트 제안 목표**: 초기 상세 경계 전송 없이 핵심 탐색 UI 5초 이내, 지도 첫 진입 총 전송량 1MB 안팎을 우선 목표로 삼고 타일 범위·품질에 따른 예외를 기록. 이는 공식 표준이 아니며 구현 전 달성 보장은 아님.
- 연속 확대·이동 20회와 탭 왕복 뒤 레이어·캐시가 무한 증가하지 않음.

## 3단계 — 첫 방문 폰트와 배치 안정화 (P2)

1. 시스템 폰트 사용과 자체 호스팅 서브셋을 시각 품질/라이선스/유지 비용으로 비교한다. 단순히 모든 한글 글리프를 하나로 합쳐 더 큰 폰트를 받게 하지 않는다.
2. CSS `@import` 연결 지연과 필요한 굵기 수를 줄인다. 단지명에 필요한 한글을 빠뜨리지 않는다.
3. 폰트 메트릭·줄 높이·검색 결과/자료 상태의 자리 확보로 화면 이동을 줄인다.
4. 웹폰트 차단·느린 폰트·캐시가 없는 조건에서도 이름·가격이 즉시 읽혀야 한다.
5. 같은 PC/회선 조건에서 최소 3회씩 비교한다. 공식 `web-vitals` 또는 동등한 검증 도구로 CLS 세션 구간을 정확히 측정한다. 단순 layout-shift 합계를 공식 CLS로 쓰지 않는다.

제안 완료 기준: 첫 화면의 폰트 전송량을 현재 약 246KB에서 의미 있게 줄이고 핵심 첫 방문 전송량 300KB 이하 가능성을 검증한다. 실제 사용자 지표는 익명·최소 정보 방식과 수집 목적을 정한 후 별도 도입한다. 표준 목표는 [Google Web Vitals](https://web.dev/articles/vitals)의 실제 방문 p75 LCP≤2.5s, INP≤200ms, CLS≤0.1을 따른다.

## 4단계 — 즐겨찾기 보관 신뢰성 보완 (P2)

1. 즐겨찾기/선택 목록의 객체 중복을 줄이고 식별자 중심으로 보관한다. 이전 저장 형식의 읽기·마이그레이션을 지원한다.
2. 읽기 제한 262,144자와 쓰기 허용 범위가 모순되지 않도록 한다. 초과 문서를 빈 값으로 취급한 뒤 덮어쓰지 않는다.
3. 저장 실패·차단·크기 초과를 사용자가 알 수 있도록 하고 마지막 정상 값은 보존한다.
4. 다운로드 백업/가져오기를 먼저 검토한다. 로그인·서버 동기화는 별도 제품 요구가 생기면 결정한다.
5. 다중 탭 동기화 방식과 병합 규칙을 정의한다.

완료 기준: 현재 464개 이중 저장 재현 사례, 1,000개 허용 범위, 차단된 localStorage, 손상 JSON, 이전 형식, 탭 간 변경, 초기화/되돌리기에서 목록이 조용히 사라지지 않는다. 테스트는 가짜 또는 격리된 저장소를 사용한다.

## 5단계 — 모바일 거래 탐색 개선 (P2)

1. 50건 고정을 모바일 20건/더 보기 등과 비교한다. 사용자가 선택한 정보 밀도를 보관하는 것도 검토한다.
2. 상단 안내·필터 요약을 간결하게 하고 결과로 이동하는 동작을 제공한다. 자료 기준일/수집 범위는 접근할 수 있게 유지한다.
3. 카드의 날짜·단지명·면적·층·가격·해제 상태를 유지하면서 여백과 반복 라벨을 조정한다.
4. 다음 거래 페이지로 이동하면 결과 시작점을 보여 주고 키보드 초점도 적절히 둔다.
5. 지도의 목록 모드에서는 불필요한 지도 생성·경계 로딩을 미룬다.

완료 기준: 320/390/768px, 200% 확대, 긴 단지명, 해제 거래, 0건, 1건, 50건 이상, 하단 고정 메뉴·모바일 키보드에서 읽기·조작이 가능하다. 페이지 높이/거래당 탐색 시간과 첫 가격 표시 위치를 기존 12,282px 사례와 비교한다.

## 6단계 — 오래 이용하거나 회선이 불안정할 때 (P2)

1. 월 자료 캐시에 용량·항목 수 한도를 두고 오래 쓰지 않은 항목을 제거한다. 활성 조회가 사용하는 자료는 유지한다.
2. 요청 시간 제한과 명시적 재시도를 제공한다. 취소는 공유 중인 다른 조회의 요청을 중단하지 않도록 구현한다.
3. 화면 복귀 시 manifest 버전만 확인하고 새 게시 자료가 있음을 알린다. 사용자가 조회 중인 기간을 몰래 변경하지 않는다.
4. 월별 인덱스 부재로 대형 원본을 받는 경로를 테스트하고, 발생 시 알림 또는 안전한 복구 방식을 정한다.
5. 지도 타일 부분 실패 안내는 실제 오류 상태에 맞게 유지한다.

완료 기준: 느린/정지/실패/복구 회선, 여러 지역 1년 조회, 기간 급변, 장시간 탐색, 게시 버전 변경 시 상태가 혼동되지 않고 무제한 다운로드·메모리 증가가 방지된다.

## 선택 후속 항목 (P3)

- 공유 URL을 안정적인 식별자로 줄이고 이전 JSON 주소도 복원.
- 공유 전에 포함되는 관심 지역 범위를 알림.
- 중요 단지 페이지의 개별 메타·미리보기·사전 생성 HTML. 실제 유입 필요를 확인한 뒤 결정.
- 지역 경계 갱신과 법정동 코드 변동을 버전별로 관리.
- 실제 휴대전화·Safari·스크린리더·색 대비 추가 점검.

## 지금 할 필요가 없는 변경

- 정상 조회가 이미 월별로 분할되어 있으므로 전체 서버/API/데이터베이스 재작성.
- 첫 방문의 약 0.4MB를 해결하기 위한 대형 프레임워크 교체.
- 실제 스크롤·도형 병목 검증 없이 거래표 전부 또는 모든 UI를 가상화.
- 지도 용량을 그대로 둔 채 Canvas로만 바꾸는 수정.
- 계정 서버·유료 인프라·완전 오프라인 앱 도입.
- 현재 잘 동작하는 기준일·미수집·해제 상태·공유 목록 보호·오류 재시도 제거.

## 단계별 결과 기록 방식

수정 시 원인 → 사용자 행동 → 변경 → 전송량/화면 준비 시간/도형 수/보관 결과 → 남은 제한을 기록한다. 영향 있는 영역의 테스트와 빌드, 공개 파일 검사, 로컬 미리보기를 확인한다. 커밋·푸시는 해당 수정 작업에 대한 사용자의 명시적 요청이 있을 때만 진행한다.
