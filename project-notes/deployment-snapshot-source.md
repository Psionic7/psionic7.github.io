# 배포 저장 DB 복구

2026-11-09 커밋 `0e4bd24`의 Actions 실행 42543636016이 `Build and check public files`에서 `통합 검색 거래 누락·중복 41465`로 실패했다.

GitHub 암호화 작업 DB에는 거래 344,521행이 있지만 아파트 대장과 새 주거 연결 정보가 없었다. 배포는 이 DB를 복원하고 내보내므로, 새 연결 정보가 들어 있는 체크아웃과 이전 거래 연결 방식이 혼합됐다. 로컬 DB에는 거래 344,494행과 검증된 대장이 있어 같은 문제가 나타나지 않았다.

## 복구

- 원격 작업 DB를 별도 로컬 복사본으로 복원했다. 기존 로컬 DB와 원격 백업은 수정하지 않았다.
- 거래 344,521행을 유지하면서 로컬의 검증된 대장 21개 테이블을 복사하고 거래 연결을 새로 계산했다. 거래 ID·원문 전체의 SHA-256 지문이 복사 전후 같음을 확인했다.
- 공식 `exportData`로 내보낸 뒤 월별 자료·원본 SQLite·검색 단지 612개가 모두 연결되는지 검증했다.
- 중복 대장 페이지 캐시는 로컬 원본에 보존하고 복구 복사본에서 제외했다. 처리된 건물대장 21,563행과 건물 5,476행, 거래 원문과 거래 수집 이력은 유지했다. 복구 DB는 기존 1GiB 보관 한도 내인 768,749,568바이트다.
- 새 암호화 백업을 저장했다. 기존 백업의 보존 정리는 수행하지 않았다. 새 백업을 재다운로드·복호화한 바이트 지문을 검증한 뒤 실패한 배포를 재실행한다.

재실행 2회차는 거래 연결 갱신이 식별 정보를 만료시킨 뒤 `listingExport`가 먼저 읽는 순서 오류로 실패했다. `prepareListingExport`가 거래 연결 갱신 → `synchronizeHousingIdentity` → 매물 추출 순서를 보장하도록 수정했다. 복원된 대장이 있고 새 연결 테이블만 없는 DB도 내보내기 전에 새 연결 체계로 변환한다. 이 코드 수정은 별도 커밋 전까지 로컬 변경이며, 원격 배포에는 아직 적용되지 않았다. 원격 백업은 복구됐으므로 코드 반영 후 같은 최신 거래 데이터로 배포를 다시 실행할 수 있다.

워크플로의 데이터 검증을 끄거나 공개 거래를 더 오래된 344,494행으로 바꾸는 방법은 사용하지 않았다. 회귀 검사는 `tests/housing-export.test.mjs`에서 새 연결 테이블이 없는 대장 DB의 최초 추출과 재실행을, `tests/daily-listings.test.mjs`에서 거래 연결 갱신 직후의 만료와 배포 내보내기 순서를 확인한다.

증거: `local/deploy-merge-proof.log`, `local/deploy-compact-proof.log`, `local/deploy-repro/final-validation.json`, `local/deploy-repair-backup.json`. 인증 정보와 암호화 키는 공개 파일에 포함하지 않는다.
