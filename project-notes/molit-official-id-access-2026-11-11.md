## 수정한 오류 처리

`server/collector.mjs`는 HTTP 오류의 XML 본문에서 코드 30을 확인해 상세 서비스 등록 실패를 표시한다. HTTP 200 본문에 같은 인증 오류가 들어와도 성공으로 처리하지 않는다. 등록 실패를 반복 요청하지 않고, 메시지에 공급자가 돌려준 키나 요청 URL을 출력하지 않는다. 기본과 상세 요청은 공식 고정 주소만 사용한다.

`pnpm data:molit:check`는 현재 키로 두 서비스를 각각 1건씩 검사한다. 응답 필드명·건수·공식 ID 필드의 관측 여부와 오류 코드만 보고한다. SQLite에 연결하지 않는다. 기본 수집 및 저장 경로는 계속 기존 기본 서비스를 사용한다.

## 승인 후 확인 순서

1. [공공데이터포털의 아파트 매매 실거래가 상세 자료](https://www.data.go.kr/data/15126468/openapi.do)에서 활용 신청·승인 상태를 확인한다. 승인 계정의 키와 현재 `MOLIT_SERVICE_KEY` 설정이 같은지 확인한다.
2. 아래 명령을 실행한다.

   ```powershell
   pnpm data:molit:check --region-code 41135 --month 202611
   ```

3. `local/data-validation/molit-access.json`에서 상세 서비스의 `status`, `httpStatus`, `detailedIdStatus`를 확인한다. `present`는 실제 응답 행에서 `aptSeq`가 관측됐다는 뜻이다. `no_rows`는 거래가 있는 지역·월로 다시 검사해야 한다는 뜻이다. `missing`이면 성공 응답의 공식 단지번호 지원 필드를 확인한다.
4. 공식 단지번호가 확인되면 같은 지역과 월의 거래를 대조한다.

   ```powershell
   pnpm data:molit:compare --region-code 41135 --month 202611
   ```

   명령은 상세 API의 전체 페이지를 검증하고 원문과 대조 결과를 `local/molit-detailed/`에 보관한다. 로컬 SQLite는 읽기 전용으로 사용한다. 분당구 이외의 지역은 `--region-code`, 별도 DB는 `--database`로 지정한다.

## 대조 결과 읽기

공식 활용명세의 상세 응답에는 `aptSeq`, `jibun`, `bonbun`, `bubun`, `roadNm`이 있다. 대조 명령은 양쪽에 있는 계약일, 가격, 면적, 층, 단지·주소, 등기·취소 정보 등으로 거래를 비교한다. 같은 값의 거래가 여러 건이면 양쪽 건수와 모든 `aptSeq`가 일치하는 경우에 기존 거래 행 번호를 후보로 기록한다. 같은 거래 그룹에 공식 단지번호가 여러 개 있거나 번호가 비어 있거나 건수가 다르면 검토 대상으로 남긴다. 한쪽에만 있는 거래도 보고한다.

후보를 실제 승인 연결에 반영하기 전에 상세 응답의 단지번호·주소를 로컬 아파트 범위와 확인한다. 공급자 번호는 접두사와 선행 0을 포함한 원문 문자열로 기록한다. 기존 거래 행 번호와 상세 행의 원문 내 순서는 대조 근거로 저장한다.

로컬 기준 DB에도 이 연결과 최신 원본을 반영했다. 두 저장본의 광고 원문은 전체를 유지하며 공통 조회 함수가 등록 동으로 제한한다. 각 차수의 기본 주소·대장 ID·실거래 ID를 보존했다. 원본 실거래 344,494건의 전체 행 해시는 수정 전후 같았다.

복원용 연결 자료는 `pnpm listings:match --max-targets 0 --write-seed`로 로컬 기준에서 다시 생성했다. 공유 연결은 대표 연결을 먼저 복원하고 양쪽 범위 해시를 다시 확인한다. 재실행, 빈 최신 광고, 대표 주소 변경, 등록 동 충돌, 공간 근거 누락과 차수별 매물 분리를 회귀 테스트로 확인했다.

실제 원문·작업 DB·보고서는 Git에서 제외된 `local/naver-shared-scope-validation/`에 있다. `current-2623.json`이 최신 수집 결과이며 `current-2623-source.jsonl`은 브라우저가 관측한 원본 응답이다. `verification.json`은 실거래 행 보존과 로컬 연결·조회 건수를 기록한다. 연결 감사의 전체 미확정 건수에는 이번 범위 밖의 기존 문제가 포함된다.

관련 Node 테스트 138개와 `pnpm test:data` 27개가 통과했다. `pnpm data:identities`, `pnpm data:export`, 연결 감사, `pnpm build`, `pnpm data:verify`, `pnpm check:publish`도 완료했다. 빌드 전후 검증은 실거래 344,494건과 월별 파일 760개를 확인했다. 로컬 미리보기 `http://127.0.0.1:5173/`는 HTTP 200으로 응답했다. Codex 브라우저 패널 열기 요청은 `queued`이며 이 세션의 브라우저 연결 목록은 비어 있어 화면의 시각 검증은 수행할 수 없었다.

## 공식 ID 저장 이관에 남은 처리 조건

최초 대조 당시 운영 `collectMonth`는 기본 API를 사용했다. 이후 [공식 실거래 단지 ID 저장](molit-provider-id-storage.md)을 구현해 상세 API를 기본 수집 경로로 전환했다. 기존 `trades.id`와 공개 정규화 열을 유지하면서 공식 ID 카탈로그·거래 연결·불변 원문 버전을 추가했고, 월별 웹 조회 자료에도 `raw.aptSeq`를 보존한다. 아래는 구현 전에 확인한 처리 조건이다.

1. 상세 원문의 `aptSeq`를 문자열로 보존하고 거래 행의 내부 ID와 공급자 종류·공식 단지 ID를 별도 관리한다.
2. 기존 거래와의 완전 일치 후보 819건부터 처리한다. 필드가 갱신된 16건은 과거 원문과 최신 관측의 관계를 기록해 검토한다. 정정 필드를 무조건 제외하면 다른 계약이나 취소 기록을 합칠 수 있으므로 중복 개수·후보 충돌도 확인해야 한다.
3. 로컬에 없는 43건은 새 관측으로 저장하고 로컬 확정 연결로 조회 범위를 결정한다.
4. 공식 ID와 기존 `source` 참조 사이의 연결을 보존한다. 보성과 임광처럼 공급자별 단지 범위가 다른 관계도 표현한다.
5. 현재 `collectMonth`의 월별 `DELETE`·`INSERT`는 거래 행 ID를 다시 배정할 수 있다. ID 연결을 저장하는 구현에서는 재수집·정정·중복 거래를 다뤄도 기존 참조가 유효하도록 갱신 방식을 함께 수정해야 한다.

## 재검사와 증거

`pnpm data:molit:compare --region-code 41135 --month <계약월>`로 상세 원문과 기존 DB 대조를 다시 실행할 수 있다. 현재 증거는 Git에서 제외된 `local/molit-detailed/`에 있다.

- `41135-<계약월>-<검사시각>.json`에 상세 XML과 대조 후보·미확정 내역을 저장했다.
- `basic-41135-<계약월>.json`에 검증 시점의 최신 기본 XML을 저장했다.
- `live-verification-2026-11-11.json`에 16건의 필드 차이, 상록마을의 기존 로컬 연결과 검사 결과를 저장했다.
- `local/verify-molit-detailed-live.mjs`는 저장된 상세 응답과 최신 기본 응답을 검증하고 원본 DB의 파일 해시가 같은지 확인한다. 같은 입력으로 재검사할 때 사용할 수 있다.

`pnpm test:data` 27개가 통과했다. 원본 DB는 읽기 전용으로 열었으며 검사 전후 SHA-256이 `67649dde6d85d2dbbeb713727e662cccda8dd0255c659f6c45e1000d4044d9bb`로 같았다. 검사 범위는 위 4개월의 분당구이며 다른 지역과 전체 과거 거래에 대한 공식 ID 확보는 남아 있다.
