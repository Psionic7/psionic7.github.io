# 현재 아파트 데이터 미매칭 원인과 해결안

작성일: 2026-11-10. 구현 커밋: `a4ec9f7468950ce29b938b5c95ac7cf592207059`.

커밋과 `origin/main` 푸시는 완료했다. [해당 GitHub Actions 실행](https://github.com/Psionic7/psionic7.github.io/actions/runs/42775955117)도 성공했다. 그러나 **실서비스 데이터는 로컬 검증 DB와 다르며, 부속시설 오분류가 배포에서 다시 나타난다.** 현재 최우선 문제는 개별 아파트 이름 검색보다 복원 DB의 재구성 순서다.

이 문서는 조사를 통해 확인한 현재 상태와 후속 해결안을 기록한다. 조사 중 원본 DB, 연결 규칙, 수집 설정을 변경하지 않았다. 아래 해결안은 추가 구현 대상이다.

## 1. 기준 자료와 로컬·실서비스 차이

[실서비스 감사 근거](apartment-data-matching-production-2026-11-10.json)는 실제 공개 사이트에서 받은 공통 카탈로그·지도·주거 배정·매물 상태다. 카탈로그와 지도·주거 배정 파일의 SHA를 확인했다. 마지막 확인은 근거 파일의 `checked_at`에 기록했다.

[로컬 상세 감사 근거](apartment-data-matching-evidence-2026-11-10.json)는 SQLite 읽기 전용 연결로 조사한 건물·필지·원천 동 번호·연결 근거다. 기계 판정의 상태와 실제 대장 내용을 함께 확인할 때 사용한다. 서로 다른 시점의 두 DB를 같은 데이터라고 취급하지 않는다.

## 2. 최우선: 복원 DB에서 옛 주거 분류가 재사용된다

실서비스 지도에는 다음 세 항목이 다시 `residential`로 나타난다. 로컬에서 같은 원천을 재구성한 결과는 모두 부속시설이며 지도에서 제외된다.

| 대장 root | 항목 | 저장 원천에서 확인한 실제 용도 | 현재 실서비스 |
| --- | --- | --- | --- |
| `hub:10891118014` | 정자동 상록마을 124번지 | 지하주차장 | 주거 root로 지도 노출 |
| `hub:10891118130` | 정자동 상록마을 121번지 | 경비실 | 주거 root로 지도 노출 |
| `hub:10891117723` | 분당동 샛별마을 41번지 | 주차장 및 부대시설, 경비실 | 주거 root로 지도 노출 |

원인은 배포 경로에서 확인했다.

1. `.github/workflows/refresh-data.yml`은 저장소의 로컬 DB가 아니라 암호화된 클라우드 작업 DB를 복원한다.
2. `scripts/automation.mjs`의 `prepareListingExport`는 기존 마스터를 사용해 거래 링크와 주거 배정을 갱신한다. `rebuildApartmentMaster`는 호출하지 않는다.
3. `server/export.mjs`도 식별 정보와 배정을 갱신하지만 저장 층별 자료에 기반한 주거 분류·마스터 재구성은 실행하지 않는다.
4. 따라서 수정된 `buildingClassification` 함수가 있어도 복원된 DB의 옛 `classification='apartment'` 값은 남는다.
5. 현재 검사는 파일 구조·해시·조회 범위·생성 세대의 일치를 확인한다. 내용 전체가 같은 옛 분류를 사용하면 이 검사를 통과할 수 있다.

즉, 푸시와 배포 성공이 로컬에서 수행한 데이터 이관의 적용까지 보장하지는 않는다. 앞선 구현 완료 보고는 로컬 검증 결과이며 이 배포 차이를 반영하지 못했다.

### 권장 해결 순서

최신 클라우드 DB를 먼저 일관되게 백업한다. 그 DB를 대상으로 원천 분류 재판정 → 마스터·거래 링크 → 주거 배정 → 매물 대상과 공통 정보 → 지도·검색 추출 순서로 구성한다. 새 API 수집 없이 저장된 표제부·층별 원천으로 먼저 재구성할 수 있다.

CLI, 관리자, CI가 같은 준비 함수를 호출하도록 모은다. 데이터에 분류 규칙 버전을 기록하고, 버전이 다르면 배포 전에 이관하거나 배포를 중단한다. 읽기 전용 공통 조회 함수에 갱신을 숨기지 않는다.

복원 DB 이관이 실제로 바뀌었으면 푸시 실행에서도 암호화 상태를 보존해야 한다. 현재 `save` 단계의 조건은 원천 보수 변경, 정기 수집, 수집을 선택한 수동 실행에만 해당한다. 이관 변경 여부도 보존 조건에 포함해야 다음 배포에서 같은 옛 DB를 반복 복원하는 일을 막을 수 있다.

검증에는 옛 분류를 가진 복원 DB fixture를 추가한다. 해당 원천을 추출했을 때 부속시설이 지도에 나타나면 실패해야 한다. 특정 운영 ID 차단 목록 대신 용도·층별 기록을 검사한다. 실거래 원본 행·ID·원문 해시의 보존도 함께 확인한다. 마지막으로 실제 배포 파일에서 세 시설이 제외됐는지 확인한다.

### 3.2 구형 연결표의 미연결 8개는 현재 미배정 5개와 다르다

로컬 구형 `apartment_trade_links` 진단은 푸른마을(벽산), 푸른마을(쌍용), 정든마을(2단지)(동아), 루체스타, 동천센트럴자이, 동천자이, 한화포레나수지동천, 에버하임을 미연결로 표시한다. 그러나 이 8개는 현대식 원천 식별에서 모두 `verified`다. 구형 연결은 준공연도 단일 비교, 유효하지 않은 옛 지번, 좁은 명칭 후보 때문에 실패했다. 구형 경고 8개를 실제 미배정 단지로 다시 합산하면 안 된다.

루체스타 1건과 에버하임 12건은 실거래 원천 분류가 APT지만 대장 용도에는 연립·다세대·업무시설·오피스텔 등이 확인된다. 이는 위치 누락과 별도의 분류 차이다. 원천 APT 분류와 법정 용도를 둘 다 보존하고 일반 아파트와 구분해 표시하는 것이 맞다.

### 3.3 수집 범위 밖 228개

## 5. 매물 수집과 연결 상태

### 5.1 현재 실서비스의 최근 수집은 실패 상태다

현재 공개 `listings/collection.json`의 일자는 **2026-11-09**, 상태는 **failed**, 오류 코드는 **inventory_unavailable**이다. 시작과 종료 차이는 약 2ms이고 대상·성공·실패 건수가 모두 0이다. 이는 매물 0건을 확인한 결과가 아니라 대상 목록을 만드는 사전 검사에서 중단된 결과다.

`collectDailyListings`는 대장 테이블 없음, 대상 지역 대장 미완료, 활성 대상 없음 같은 조건을 이 오류로 반환한다. 공개 결과에는 어느 테이블·지역이 실패했는지 저장되지 않아 그 하위 원인까지 확정할 수 없다. 당시 복원 DB 또는 해당 실행의 진단 정보가 필요하다.

기존 관측 그룹 391개는 보존돼 있다. 그룹별 광고 행 합계는 22,198건, 광고 번호 기준 고유 광고는 20,060건, 네이버 단지 번호는 344개다. 같은 광고가 여러 대장 선택에 들어갈 수 있으므로 이 수치를 구분하며 주택 수로 합산하지 않는다. 이 자료를 11월 9일 수집 성공 결과로 표시하면 안 된다.

해결은 수집 사전 검사에 누락 테이블·미완료 지역·규칙 버전의 구체적인 실패 사유를 남기는 것이다. 최신 DB의 대장·배정을 준비한 후 대상 목록을 다시 생성한다. 이전 관측 시각과 수집 실패 상태는 유지하고 새 관측에 성공한 항목만 갱신한다.

### 5.2 68개 검색 미확정·13개 시간 초과는 로컬의 이전 수집 결과다

로컬 11월 8일 보고에는 대상 472개 중 성공 391개, 검색 미확정 68개, 시간 초과 13개가 있다. 실서비스의 11월 9일 대상 0개 실패와 섞어 현재 수집 결과처럼 보고하지 않는다.

68개는 이름·주소·실제 관측 위치가 검증되는 네이버 단지를 확정하지 못한 사례다. 미확정은 매물이 없다는 뜻이 아니다. 임대·공공주택은 매매 상품이 없을 가능성도 있지만 현재 저장된 검색 실패 기록만으로 단정할 수 없다. 분당동 10개, 수내동 9개, 야탑동 9개 등에서 많이 발생한다. 전체 목록은 로컬 상세 근거의 `listing_unresolved`에 있다.

13개는 모두 `timeout`이다. 양지마을 6개 지번, 파크타운 2개, 동양정자파라곤, 파크뷰, 봇들마을, 성남판교 경기행복주택, 진산마을삼성5차 1167번지가 포함된다. 정확한 13개 목록은 근거 JSON을 기준으로 한다. 검색 실패와 네트워크·브라우저 시간 초과는 다른 원인이므로 재시도와 검증 절차를 나눈다.

검증된 네이버 번호가 있는 대상은 번호를 먼저 사용하고 실제 주소·위치를 재검증한다. 신규 검색 미확정은 공식 주소 코드·차수·등록 동을 확인한 뒤 재검색한다. 일반 이름이나 같은 우편번호만으로 연결하지 않는다.

## 6. 그 밖의 대장 품질 경고

로컬 원천에는 주건축물 수 불일치 36개, 주거 용도 검토 기록 233개, 필지 해석 실패 기록 118개, 공식 좌표 코드 누락 2개가 있다. 앞의 두 종류는 root 경고와 건물 기록이 섞여 있으므로 숫자를 합산해 미매칭 단지 수라고 부르면 안 된다.

예를 들어 총괄 대장 주건축물 22동과 연결 표제부 21동, 또는 9동과 11동 같은 차이가 존재한다. 수집 범위 밖 건물, 상위 대장 계보, 부속시설을 포함하는 집계 정의가 원인 후보다. 모든 차이를 '주거동 누락'이라고 단정할 수 없다. 상위·하위 대장 ID, 건물 용도와 폐쇄·전환 상태를 확인하고 집계 정의를 일치시켜야 한다.

## 8. 조사 재실행과 검증

로컬 DB가 있는 환경에서 다음 순서로 재실행한다. 상세 감사 명령은 읽기 전용이고 공개 파일과 DB의 공통 세대가 다르면 중단한다.

```powershell
pnpm audit:matches --output local/data-validation/apartment-matches-current.json
node scripts/audit-apartment-data-coverage.mjs --audit local/data-validation/apartment-matches-current.json --output local/data-validation/apartment-data-coverage.json
pnpm test:data
pnpm check:publish
```

최초 구현의 Node 검사 321개와 화면 검사 182개가 통과했고, 이번 보고 작업에서는 상세 감사의 행 수 합계·미배정 분해·공개 세대 일치·17개 공간 후보 일치를 실제 자료로 확인했다. 데이터 필수 검사 24개도 다시 통과했다. 이 성공은 위 배포 원천 분류 문제를 해결했다는 뜻이 아니다. 해당 내용 판정 검사가 추가로 필요하다.

실서비스 근거는 외부 수집을 다시 실행한 자료가 아니라 실제 배포 파일을 읽은 스냅샷이다. 후속 배포·수집으로 수치가 달라지면 `checked_at`, 공개 manifest, 생성 세대를 먼저 비교한다.
