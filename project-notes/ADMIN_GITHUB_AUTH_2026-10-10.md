# 관리자 GitHub 로그인

## 분석
현재 Pages 관리자 화면은 긴 GitHub 토큰을 직접 받아 GitHub API를 호출한다. GitHub Actions Secrets는 실행 중인 Actions 작업에서 읽을 수 있으며 정적 페이지에 비밀 값을 주입하면 공개된다. 사용자는 GitHub 계정으로 로그인하고 작업용 토큰은 서버 Secret에 보관하는 방식을 요청했다.

## 계획
1. GitHub 작업 코드를 공유 모듈로 분리하고 인증 서버가 기존 설정 저장·수집·이력 기능을 수행하게 한다.
2. GitHub OAuth의 authorization code와 PKCE S256, 일회성 state와 브라우저 확인 쿠키를 사용한다. 서버에서 계정을 확인하며 저장소 소유자 ID와 로그인명이 일치해야 접속한다.
3. 로그인 세션은 HttpOnly 쿠키와 Durable Object로 관리한다. 동일 출처 요청·CSRF 확인, 로그인 시작 제한, 세션 만료·로그아웃·Secret 변경 시 세션 무효화를 적용한다.
4. 기존 Pages의 토큰 방식은 서버 연결 전에도 동작하게 유지하고 GitHub 로그인 포털 주소가 구성되면 해당 포털 접속 링크를 표시한다. 새 포털에는 토큰·비밀번호 입력을 제공하지 않는다.
5. 서버 인증·권한·설정 경쟁·비밀 값 비노출, 프런트엔드 재접속·저장·수집·로그아웃과 실제 모바일 화면을 검증한다.
6. GitHub Secrets를 서버 Secrets로 전달하는 수동 배포 절차와 OAuth App 등록 항목을 문서화한다. Cloudflare 계정과 OAuth App 자격증명은 아직 확인되지 않았으므로 실제 외부 배포 완료로 보고하지 않는다. 후속 요청에서 사용자가 현재 작업의 커밋·푸시와 가능한 외부 설정을 명시적으로 요청했다.


## 구현 결과

- GitHub OAuth 로그인 전용 포털, 서버 작업 API, 브라우저 세션 클라이언트와 공개 사이트 접속 링크를 구현했다. 새 포털에는 토큰이나 비밀번호 입력 필드가 없다.
- 공유 GitHub 작업 모듈로 기존 설정 저장·수집·이력 기능을 재사용한다. 서버는 저장소 소유자 ID와 로그인명을 확인하고 작업용 토큰의 권한도 확인한다. OAuth 토큰은 계정 확인 중에만 사용하며 저장하지 않는다.
- PKCE S256, 10분짜리 일회성 state, 별도 브라우저 확인 쿠키, IP별 로그인 시작 제한, 4시간 HttpOnly 세션, 동일 출처·CSRF 검사, 로그아웃 세션 삭제, Secret 변경 시 무효화를 적용했다. SQLite Durable Object에서 로그인 state 소비와 횟수 계산을 트랜잭션으로 처리한다.
- 설정 저장은 서버의 지역 목록과 현재 Git SHA로 검증한다. 브라우저가 보내는 workflow나 catalog는 사용하지 않는다. 진행 중인 수집·배포가 있으면 추가 변경을 거부한다.
- GitHub Secrets를 서버 Secrets로 전달하는 수동 배포 워크플로를 준비했다. UI 빌드에는 인증 비밀 값을 제공하지 않는다. 포털 주소가 설정되기 전에는 기존 토큰 접속이 유지된다.
- 분석·계획·결과는 이 문서에, 실제 OAuth App 등록·변수·Secrets·배포 절차는 auth-admin/SETUP.md에 기록했다.

## 검증 결과

- React: 15개 파일, 90개 테스트 통과. 기존 84개 회귀 테스트와 신규 세션 UI/API 6개를 포함한다.
- 인증 서버: 13개 테스트 통과. 소유자 제한, state 쿠키 확인·만료·동시 재사용, PKCE, 비밀 값 비노출, Origin/CSRF, 요청 크기 제한, 설정 경쟁, 로그아웃·만료·Secret 교체, 로그인 횟수와 저장소 정리를 검사했다.
- 관리자 포털과 공개 사이트 빌드 통과. Wrangler 4.136.3 서버 dry-run 통과. 호환 날짜는 검증한 런타임이 지원하는 2026-09-28로 고정했다.
- 실제 로컬 workerd + SQLite Durable Object에서도 로그인 시작, state 소비·취소, 비인증 세션 거부와 동시 로그인 제한을 확인했다. 실제 GitHub OAuth 토큰 교환·쓰기 작업은 하지 않았다.
- 실제 브라우저에서 모의 GitHub 응답으로 로그인 복귀, 지역 지도 표시, 새로고침 접속 복원, 설정 저장·수집 요청, 로그아웃 세션 폐기, 소유자 거부 안내를 확인했다. JavaScript 오류가 없었고 390px 모바일에서 가로 넘침이 없었다.
- 브라우저 저장소에 토큰·인증 정보를 저장하지 않으며 세션 쿠키가 document.cookie에 나타나지 않음을 확인했다. 검증용 예시 작업은 모의 GitHub 클라이언트만 사용했다.

## 현재 상태와 남은 설정

코드 구현과 로컬 검증을 완료했고, 후속 요청에 따라 변경을 커밋·푸시 범위에 포함했다. GitHub API로 저장소 설정을 확인한 결과 기존 수집용 Secrets 3개만 있으며 새 관리자용 Secrets·Variables는 등록되지 않았다. 로컬에서도 필요한 OAuth·Cloudflare 설정을 찾지 못했다. Wrangler의 인증 상태도 비로그인으로 확인했다. 사용자는 Cloudflare 계정이 없다고 알려 주었다. 따라서 실제 관리자 서버 배포와 GitHub 계정 로그인 활성화는 최초 호스팅 계정·OAuth App 등록 후 진행해야 한다. 비밀 값은 저장소 Secrets로 직접 등록하며 코드나 채팅에 공개하지 않는다.

## 요약

GitHub 로그인 버튼으로 관리자에 들어가고 긴 토큰은 서버 Secret에만 보관할 수 있는 구조를 준비했다. 실제 사용을 위해서는 SETUP.md의 최초 서버·OAuth App 설정과 수동 배포가 필요하다. 로컬 미리보기는 모의 응답을 사용한 화면 확인용이다.
- 최종 게시 파일 검사 통과: 206개 파일. 서버 dry-run이 만든 중간 파일은 Git에서 제외되는 local 폴더로 옮겼으며 실제 비밀 값은 게시 대상에 포함하지 않았다.
- 수동 배포에서 사용하는 설정 생성 스크립트와 생성 설정의 Wrangler dry-run도 통과했다. 예시 도메인·Client ID로 검증했으며 실제 서버는 배포하지 않았다.

## 호스팅 계정이 필요한 이유

GitHub는 로그인 계정을 확인하는 인증 제공자이고 Cloudflare는 이번 구현의 관리자 서버 호스팅 제공자다. GitHub 로그인 자체는 Cloudflare에 종속되지 않는다. GitHub Pages는 정적 사이트이므로 이번 요구 사항인 서버 비밀 값 보관, OAuth 코드 교환, 세션 관리와 관리자 작업 처리를 위해 별도 서버가 필요하다. 현재 구현은 Workers와 Durable Objects를 사용하므로 Cloudflare 계정이 필요하다. 기존 서버나 다른 호스팅에 배포하려면 해당 플랫폼의 세션 저장·배포 방식으로 서버를 이식해야 한다.

Cloudflare 계정 생성과 OAuth App 등록은 실제 계정으로 진행해야 하는 최초 설정이다. 브라우저 자동화 런타임이 두 번 종료되어 로그인 상태를 읽거나 해당 설정 화면을 조작하지 못했다. 미완료 외부 설정을 완료로 보고하지 않는다.
