# 데이터 소유권과 공급자 단지 ID 운영 규칙

확정일: 2026-11-10. 사용자가 지정한 프로젝트 운영 기준이다. 이후 설계·구현·수집·배포·보고에서 이 문서를 우선 적용한다. 과거 구현 설명과 충돌하면 현재 코드가 이 기준을 충족하는지 확인하고 차이를 수정 대상으로 기록한다.

2026-11-12 운영 변경: 사용자 요청으로 GitHub의 네이버 매물 수집·접속 진단과 웹의 매물 표시를 중단했다. 아래 소유권·저장·ID 규칙은 유지하되, 재개 요청 전에는 매물 수집을 예약·수동 GitHub 작업에 연결하지 않는다. 기존 원천 매물·수집 이력·로컬 확정 연결과 로컬 전용 도구는 보존하고, GitHub에서는 실거래 수집·검사·배포를 계속한다.

이 문서는 운영 규칙을 확정한 것이다. 현재 코드와 DB가 모두 이 구조로 이관됐다는 뜻은 아니다. 현재 차이는 마지막 절에 구분했다.

## 1. 아파트 기준은 로컬 확정본 하나다

로컬에서 아파트 대장·기본 속성·주거 분류·위치·필지·구역을 수집하고 확정한다. 네이버 단지 ID와 실거래 공급자 단지 ID의 연결도 로컬에서 확인하고 확정한다.

GitHub는 이 기준본을 읽어 실거래와 네이버 부동산 매매 매물을 수집·보존한다. 웹은 로컬에서 확정한 ID 연결 관계로 각 자료를 함께 보여준다. GitHub의 과거 수집 DB, 웹 검색 결과, 이름·주소 유사도가 로컬 확정본을 대체할 수 없다.

| 자료 | 소유·확정 주체 | GitHub가 수행하는 작업 |
| --- | --- | --- |
| 아파트 기본 정보·대장·분류·위치·구역 | 로컬 | 확정된 기준 버전을 읽음 |
| 아파트와 공급자 단지 ID의 연결 | 로컬 | 확정된 대상·범위를 읽어 수집과 조회에 사용 |
| 네이버 부동산 매매 매물 | GitHub | 네이버 단지 ID로 수집하고 네이버 매물 테이블에 저장 |
| 실거래 원문·정정·취소 | GitHub | 공급자 단지 ID를 보존해 실거래 테이블에 저장 |
| 수집 시각·오류·미시도·과거 관측 | GitHub | 수집 이력으로 보존 |
| 거래 배정·검색·화면용 조회 자료 | 파생 결과 | 확정 연결과 최신 수집 자료를 조합해 생성 |

아파트 기준본을 갱신하는 작업과 이미 승인된 ID의 새 매물·실거래를 받는 작업은 별개다. 클라우드에서 새 연결 후보를 발견하더라도 검토 자료로 보관하고, 로컬 확정 연결로 자동 승격하지 않는다.

## 2. 공급자 고유 단지번호를 ID로 사용한다

네이버 아파트는 네이버 단지 고유번호, 실거래 원천 아파트는 실거래 공급자의 공식 단지 고유번호를 사용한다. 이름·지번을 조합해 공급자 고유번호를 새로 만들지 않는다.

| 식별자 | 의미 | 다른 용도로 사용하지 않는 값 |
| --- | --- | --- |
| 로컬 아파트 ID | 로컬 기준 아파트와 대장 범위를 가리킴 | 공급자 공식 단지 ID와 같은 번호라고 가정하지 않음 |
| 네이버 단지 ID | 네이버의 특정 단지 | 광고 번호나 이름을 단지 ID로 사용하지 않음 |
| 실거래 공급자 단지 ID | 실거래 원천의 특정 아파트 | DB 거래 행 번호나 이름·주소 복합값을 단지 ID로 사용하지 않음 |
| 네이버 광고 ID | 특정 광고 | 단지 ID나 고유 주택 ID로 사용하지 않음 |
| 개별 거래 행 ID | 특정 거래 기록·원천 관측 | 아파트 단지 ID와 구분 |

공급자 ID는 문자열로 보존한다. 공급자가 정의한 지역 접두사·구분자·유일성 범위를 임의로 제거하지 않는다. 여러 공급자를 함께 다루는 연결 키에는 `provider`와 `provider_apartment_id`를 함께 사용한다. 네이버의 `12345`와 다른 공급자의 `12345`는 서로 다른 ID다.

공식 ID가 현재 수집 응답에 없으면 그 사실을 기록하고 지원 API·공식 보강 자료를 확인한다. 확인 전에는 해당 자료를 식별 미확정 상태로 보존한다. 내부 임시 키가 필요해도 공급자 공식 ID와 다른 필드·종류로 표시하며 임의의 공급자 번호를 만들지 않는다.

네이버 링크는 단지 ID에 대응하는 정식 링크를 저장하거나 생성해 제공한다. 수집·연결의 기준은 공급자 단지 ID다. 검색 URL이나 광고 상세 URL을 단지 고유번호 대신 사용하지 않는다.

## 3. 아파트·네이버 매물·실거래·연결을 나누어 저장한다

아래 이름은 논리적 역할이다. 새 SQL 테이블명을 이미 확정하거나 이관 완료한 것으로 해석하지 않는다.

| 논리적 저장 영역 | 필수 내용 |
| --- | --- |
| 아파트 기준 테이블 | 로컬 아파트 ID, 이름·주소·위치·구역, 분류, 출처, 기준 버전 |
| 공급자 단지 테이블 | 공급자 종류, 공식 단지 ID, 공급자 단지명·링크·원천 메타데이터 |
| 로컬 확정 연결 테이블 | 로컬 아파트·구역 ID, 공급자 종류·단지 ID, 연결 범위, 확인 근거·시각, 활성 상태, 연결 버전 |
| 네이버 부동산 매물 테이블 | 네이버 단지 ID, 광고 ID, 매매 조건·가격, 관측·수집 시각과 원문 |
| 실거래 테이블 | 실거래 공급자 단지 ID, 개별 거래 행 식별자, 계약·가격·면적·정정·취소 정보와 원문 |
| 수집 이력 테이블 | 대상 공급자 ID, 시도·성공 시각, 오류·미확정·미시도 상태 |

아파트 한 곳에는 여러 매물과 여러 거래가 있다. 따라서 단지 ID 하나만 매물·거래 테이블의 행 기본키로 사용해 이전 행을 덮어쓰면 안 된다. 각 행은 별도로 식별하고 단지 ID를 참조한다. 외부 계약 ID가 없는 자료는 원문과 중복 개수를 보존하는 행 식별 정책을 따로 적용한다.

네이버 매물 데이터를 아파트 기준 속성으로 덮어쓰거나, 실거래 행을 네이버 매물 행에 합쳐 저장하지 않는다. 웹 조회용으로 두 자료를 묶은 파생 파일을 생성할 수 있으나 원천 저장 영역과 출처는 분리한다.

## 4. 연결 관계는 로컬에서 명시적으로 확정한다

2026-11-14 실거래 공식 번호의 확정 저장 영역은 `apartment_molit_sources`다. 공급자 단지 번호와 내부 원천 단지 참조를 구분해 보존하며, 동일 계약을 대조한 근거와 확정 시각을 함께 저장한다. 일부 월의 `raw.aptSeq` 관측 목록을 승인표 대신 사용하지 않는다. 검토·적용 명령 `data:molit:link`는 편집 가능한 로컬 원본에서만 실행한다. 동결 기준본은 이 테이블과 동일한 공급자 조회 연결을 포함하고 클라우드에서 읽기 전용으로 설치한다.

한 공급자 단지가 여러 대장 root·주소 구역을 포함할 수 있다. 같은 실제 단지도 공급자별 범위가 다를 수 있다. 단지마다 네이버 ID 하나와 실거래 ID 하나가 반드시 일대일 대응한다고 가정하지 않는다.

로컬 연결 테이블에는 `root`, `cohort`, `source` 같은 기존 선택 범위와 필요한 등록 동 범위를 함께 보존한다. 웹이 어떤 매물·거래를 해당 선택에 포함할 수 있는지는 이 명시적 관계가 결정한다.

화면에서 이름·주소·우편번호·좌표 근접도로 다시 병합하지 않는다. 공급자 번호 하나가 여러 주소를 묶으면 공급자 원본을 보존하면서 로컬에서 확정한 범위로 조회한다. 동 정보가 없는 과거 거래를 모든 하위 단지에 복사하지 않는다.

수집 실패·시간 초과·매물 0건으로 로컬 확정 연결을 삭제하거나 다른 단지로 바꾸지 않는다. 실제 관측 주소와 기준 정보가 충돌하면 수집 상태를 검토 필요로 기록하고 원본 연결과 관측 이력을 보존한다. 연결 수정·해제는 로컬에서 검증한 새 기준 버전으로 반영한다.

## 5. GitHub 수집과 웹 조회의 기준

1. 로컬 아파트·공급자 연결 기준본의 버전과 무결성을 확인한다.
2. 해당 기준본의 확정 공급자 단지 ID로 수집 대상을 만든다.
3. 네이버 매물과 실거래를 각각의 원천 테이블에 저장한다.
4. 웹은 로컬 연결표를 통해 공급자 ID와 로컬 아파트·구역을 연결해 보여준다.
5. 조회 자료에는 사용한 아파트·연결 기준 버전과 수집 자료 버전을 기록한다.

실거래 수집 API가 지역·월 단위 응답을 제공하는 경우에는 응답 원문을 보존하고 공급자 단지 ID와 로컬 연결표로 후속 연결한다. API에 단지별 요청 기능이 있는지 확인하지 않고 있다고 가정하지 않는다. 미연결 응답을 임의의 단지에 배정하거나 원문에서 삭제하지 않는다.

기준본이 없거나 연결 버전이 맞지 않으면 수집·배포를 명확히 중단한다. 과거 클라우드 아파트 테이블, 이름 검색, 임시 내부 키로 기준을 대체하지 않는다. 특정 공급자 ID가 미확정인 경우 그 대상의 미확정 상태를 보고한다.

## 6. 클라우드 복원은 수집 결과 보존용이다

클라우드 수집 이력 DB는 이전 실행의 실거래·매물·원문·수집 이력을 다음 실행에 이어 주는 저장소다. 아파트 기준 DB가 아니다. 복원된 DB에 아파트 정보가 남아 있어도 로컬 확정본보다 우선하거나 기준을 덮어쓸 수 없다.

로컬 전체 DB로 클라우드 전체 DB를 교체하지 않는다. 클라우드에 더 최신인 실거래·매물 관측이 있을 수 있기 때문이다. 아파트·연결 기준본과 수집 결과의 갱신·보존 경로를 분리한다.

## 7. 현재 구현과의 차이

다음은 2026-11-10 로컬 코드·DB 확인 결과다. 이 문서 작성으로 해당 이관이 수행된 것은 아니다.

- 네이버 단지번호는 `complex_no`로 저장돼 있고, 매물에는 별도 광고 ID가 있다. 현재 일부 매물은 `naver_listing_snapshots.group_json` 묶음으로 저장되므로 위의 논리적 매물 테이블과 완전히 같은 물리 구조는 아니다.
- 실거래는 `trades`와 `raw_json`에 저장한다. 현재 `trades.id`는 거래 행의 정수 기본키다. 아파트 공급자 고유번호가 아니다.
- `src/housing-identity.mjs`의 현재 `sourceIdentityId`는 지역·동·지번·이름 조합이다. 이것은 기존 내부 호환 키이며 실거래 공급자의 공식 단지 ID를 대체하지 못한다.
- 2026-11-10 당시 수집기는 `server/collector.mjs`의 `getRTMSDataSvcAptTrade`를 사용했다. 당시 확인한 로컬 거래 344,494건의 원문에는 `aptSeq` 값이 없었다. 이후 상세 API 수집·공식 ID 저장을 구현한 범위는 아래 후속 결과에 기록한다.
- 2026-11-10 당시 클라우드 복원 DB에 옛 아파트·연결 정보가 섞여 있었다. 이후 기준본 전달과 소유권 강제를 구현한 범위는 아래 후속 결과에 기록한다.

공식 단지 ID를 도입할 때 기존 원본 거래·관측과 북마크·즐겨찾기·공유 URL의 내부 참조를 임의로 변경하지 않는다. 내부 호환 키와 새 공급자 ID 사이에 검증된 이관 관계를 두고 재실행 시 같은 결과가 나오는지 검사한다.

2026-11-11 후속 구현에서 운영 월 수집을 상세 API로 전환했다. 로컬 분당구 2026년 7·9·10·11월의 878건과 공식 단지 169개를 관측했으며 기존 835건의 거래 ID·원문과 로컬 대장·네이버 승인 연결을 보존했다. 현재 거래와 공식 ID는 `molit_trade_identities`, 공급자 단지는 `molit_apartments`, 이전 원문·실행은 불변 버전과 실행별 행 테이블에 저장한다. 전체 과거 월의 공식 ID 보강과 버전이 있는 로컬 승인 연결 기준본 전달은 후속 대상이다.
